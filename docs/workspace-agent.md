# The workspace agent

The **workspace agent** is one long-lived agent per person that works at a high level across the whole workspace: it looks at what its person can see, plans, hands building to each tile's own agent, does things in a tile for its person once they approve, keeps a notebook, and reports back. It acts with its person's access and never more, and everything with a side effect is approved by that person in xbin's own chrome, where xbind — not the agent — keeps and checks the approval.

This page is for the people who run a workspace and for tile authors: what the agent is, what it reaches, how its approvals work, what a tile should declare, and what the language model's provider sees. The rules behind it are in [auth.md §Delegation](/docs/auth.md#delegation-a-persons-workspace-agent); the routes in [protocol/delegation.md](/docs/protocol/delegation.md); the org rules in [protocol/orgs.md](/docs/protocol/orgs.md); the connector in [llm.md](/docs/llm.md).

## What it is

- **A sealed component at `xbin/wsagent`.** Its code ships inside xbind and is always the running release's: nothing of it is copied into the workspace, so there is no instance to merge, no terminal, no code tab. It is the agent template's backend (`builtin-templates/agent`) started in *workspace mode* (`XBIN_AGENT_MODE=workspace`, set by xbind from its own table) — the same engine, with one profile, one fixed class and a closed list of routes.
- **One partition per person.** Each person's agent is their own partition: its conversations, its notebook and its settings are in that person's encrypted data, and it calls xbind as that person and nobody else.
- **Sessions.** A person has one default session, **Main**, made on first use: long-lived, renamable, never archived. They can open more, each with its own name, scope (which orgs and tiles it looks at) and model. Old turns are compacted, and the agent can search and re-read them. A session never carries a conversation to a model that an org whose data it has read doesn't allow: the change is refused, and a new session is offered. What a conversation has read is kept with the conversation, not only with xbind's record of it: when xbind renews a session's record (after a day unused), the agent gives the new one everything the conversation holds before it reads or calls a model again — and if an org's rules no longer allow the session's model, the session stops there and says so, offering the model it was on or a new session.
- **Off until set up.** Nobody has an agent until an admin connects a language model ([llm.md](/docs/llm.md)), turns workspace agents on and chooses who gets one ([Setting it up](#setting-it-up)). A workspace that does none of that sees nothing new: no chip, no notice, nothing running. A person pauses their own agent at any time; pausing stops its every call at once.

## What it can reach

Everything goes through xbind's delegation, as the person, under the delegation cap — a closed list:

| It can | How |
|---|---|
| see what its person sees | the map of their tiles, screens and orgs; a tile's status and what it reports; a tile's log where the person may open a terminal; xbin's docs; a tile's `API.md` |
| call a tile's own API | `GET` runs; any other method asks the person first, with the exact call shown |
| start a tile agent | a coding-agent session in the tile, opened as the person and marked "started by your agent"; asked every time (or the person's preference). The model never picks the coding agent: it is the person's choice among what the tile's org allows, and its mode and network are the person's preferences |
| look at a tile's page | a read-only preview of one tile as the person sees it: the agent gets the page as text |
| steer the tile agents it started | message, read status and result, stop a turn — never one the person started themselves |
| ask a sub-agent about a tile's code | a read-only research sub-agent lists and reads the tile's files through `/code/tree` and `/code/file` and answers in words |
| create a tile from a template | where the person may create; asked every time |
| propose admin changes | only for an admin who turned it on: a batch the person reviews; xbind applies what they tick, as them |
| remember | a notebook of pages the person can read, edit and delete |

What a session is connected to follows the tile's org on every call: an org can keep workspace agents out, allow private models only, or name the coding agents allowed on its tiles. The session's connection line ("14 tiles · 3 orgs connected · 6 not connected") is xbind's; a blocked tile is never named to the agent.

### What it never does

The workspace agent never reads or changes a tile's code itself: a tile's own agent builds, and a research sub-agent reads and summarises. It never answers a tile agent's permission request or question, since those are its person's to answer, and a message it sends a waiting tile agent is held until they did. It can't delete or disable a tile, open a terminal, use the web, change passwords, devices or sign-ins, call the admin API, or approve anything: every approval is its person's own click in xbin's chrome or the app. It can't see a tile that isn't connected in its session, and it can't act for anyone but its own person.

## How approvals work

The agent **asks**; the person **decides**, in chrome the agent's page can't draw in; xbind **keeps** the decision and checks it on the call.

1. The agent files the side effect exactly as it will be sent (`POST /delegate/requests`): the method, path and body of a tile call, a tile agent's start, a tile's creation. Before that it asks xbind what the call would be (a dry run) — every changing tool of the agent has that form.
2. The person sees xbind's description beside the agent's words (which are quoted as the agent's), and allows it once, allows it as a standing approval, or denies it. A request waits 24 hours.
3. Approved, the request is a ticket: once, within 15 minutes, for that exact call. The agent's backend makes the call and gives the answer to the model; denied, expired or withdrawn, the model is told that instead.

Nothing is allowed while the agent is stopped. While workspace agents are off, the agent is paused or held, or its person has none, the sheet says why where Allow (or Apply) is, and xbind refuses an Allow sent anyway; Deny and Reject still work. Switching workspace agents off, taking a person's agent away, or disabling them withdraws what was waiting for them, so nothing approved then runs the moment it is back; a pause or a hold keeps it, to decide after resuming.

Starting a tile agent is approved with its brief: the brief is part of the ticket, xbind shows it as what the session is told first, and xbind sends it. What the agent messages that tile agent afterwards is not approved message by message — the tile agent's own mode, asking the person before it acts, is the guard there.

A request holds nothing up: the agent is told it is pending and goes on, or ends its turn, and the outcome reaches the conversation as an update when the person decides — hours later if need be. Meanwhile it still hears from the tile agents it started. A message from the person is never taken for the decision. xbind tells the agent's backend that something changed with a notice that carries ids and kinds only; the backend reads the state again through the API, so a forged or repeated notice changes nothing — and it reads everything it waits on again when it starts and while anything is open, so a notice that never arrives costs a delay, not a stuck conversation.

Admin changes are never calls. An admin's agent proposes a change set (grants, bindings, org shares, limits); xbind writes each line, its before and after and its warnings; the person ticks what to apply.

## Using it

A person meets their agent in **the dock**: a panel beside the canvas, opened with the **workspace agent** chip in the top bar (or Ctrl+J / ⌘J when no field or terminal has the keys), or about one tile with **Ask my agent about this tile** in that tile's ⋯ menu. The chip carries the number of things that wait for them; on a narrow screen the dock is the whole page. A workspace whose shell has no chip — a scaffold from before it — uses **`/xbin/agent`**, the same dock as a page of xbind's own; such a shell shows one alert that names the page, per person, until they dismiss it.

The dock's header is xbin's, and so is everything a person decides in it; the agent's own conversation is a page in a frame below, and it can draw nothing in the header or over it.

- **Needs you** lists what waits: requests for approval, proposed admin changes, and tile agents the person's sessions wait on.
- **An approval** opens as a sheet from the header. It shows what xbind read of the request — the tile and the person's level on it, the exact call, what is sent (text, or "binary", its size and hash), whether it can be undone — with the agent's own sentence quoted below as the agent's. A character that reorders or hides text (a bidi control, a zero-width one) in anything the agent wrote is shown as its escape, ⟨U+202E⟩, under a line that says so. The choices: **Allow once**, **always allow this exact action**, or — marked as wider, with a second step whose first button is *Go back* — **every change to this tile** for a time. A tile agent's start shows the coding agent, the model, the mode ("asks before acting", or the wording of a mode that doesn't — there *Deny* is the first button), the network and the brief exactly as sent. Allow answers only to the person's own click, a moment after the sheet shows; Enter never allows, Esc leaves it for later.
- **Admin changes** open as a dialog over the workspace: a line an item with its before and after; an item with a warning (it makes something public, opens a port, lets a tile reach the internet) starts unticked; an item xbind would refuse is shown with the reason and can't be ticked. Applying asks for a recent sign-in when there is none. The results name what was applied, what failed and what was out of date; **Undo** proposes a new set to review — it undoes nothing by itself.
- **Approvals** lists the standing approvals, each with **Take back**. **What my agent did** is the person's log in sentences (changes, refusals, everything). **Preferences** — opened from the dock's own menu, never by the agent's page — holds whether the agent may start tile agents without asking, the mode each coding agent starts in when it does — a pick among the modes that ask before acting; the ones that don't are named, with why, and can't be saved — and, for an admin, whether it may propose admin changes.
- **A control that widens what the agent may do** — "start without asking", a wider network, other tiles' APIs, the admin opt-in, an approval's wider scope — answers like Allow: only the person's own click, a moment after it shows, while nothing covers it; Enter never.
- **Pause** stops the agent's every call at once; only the person resumes it. While it is paused — or turned off, held, or not given to its person — a message to it is answered without the model: the conversation says which switch is on and who can change it where, nothing is sent, and the words stay in the message box until the person sends them again.

In place of the conversation the dock says why there is none: not set up (an admin sees the three steps), no language model connected, turned off for the workspace, paused, or held after a restart or a downgrade.
## The agent's page

The conversation with the agent is its own page — the sealed component's frontend, the agent template's `ws/` page — framed by xbin's dock (or `/xbin/agent`). It shows:

- **The session in view** and a switcher: Main always first and never archived; other sessions with their name, scope, model and status; New session… (it copies the scope and model of the one in view and starts empty), Rename, Archive (archived ones fold under Older).
- **The scope chip**, always in view: xbin's line ("14 tiles · 3 orgs connected · 6 not connected") and the model. It opens a panel: the four totals; orgs unfolding to tiles, each *connected*, *hidden by you*, *blocked* (with the org's own sentence) or *no access*; ticks staged and applied with one button; the model with a what-if before anything changes, and a change the conversation's data doesn't allow drawn as "This session can't move to …" with a new session as the way forward. Scope is focus, not permission, and the panel says so: a blocked tile can't be ticked.
- **The conversation**, with the agent's own cards where it made them: the plan (which steps only read and which will ask), the brief for a tile agent (Goal, Done when, Leave alone, Check by — editable, what the tile agent is told first, what it will run on, a pick among the coding agents the tile allows), a request waiting for approval (what, for which tile, when it expires) and afterwards what came of it, a tile agent it started (its status as a glyph and a word, its last line, Open — or Answer when it waits for you: only you can answer it), xbin's refusals with the way forward, and the agent's questions as choices with "Something else".
- **An empty state** for a new session: what the agent can and can't do in this session, and starters built from your own tiles. A starter fills the message box; it never sends.
- **The notebook**: every page, read, edited, added or deleted by you; a page a session may not read is listed but closed, with the reason; a page marked with orgs says so, and that the way to clear the marks is to delete it and have it written again.
- **Banners** for what stops it: paused, a used-up quota, turned off by an admin, xbin updating, no connection (your draft stays and is not sent).

**The page grants nothing.** It renders what a model wrote, so every approval — a tile call, a tile agent's start, an admin change set, resuming — is drawn by xbin's chrome from xbind's own reading of the request. The page asks the chrome to open one by its id (`xbin:agent-open-request {id}`, `xbin:agent-open-changeset {id}`; a tile agent's session with `xbin:open-session {session, tile}`, or a new one of a tile's own agent with a draft — `{session: "new", tile, draft}` — when the agent redirects a request about code: the tile's window opens on a new session's launcher, and the draft waits, unsent, in the composer of the coding agent you pick. The draft comes from the agent's page, so xbin labels it as text the page suggests, for you to read and edit — never as your own words; a shell from before this gets a plain link to the tile instead), and the chrome tells the page what it was opened about (`xbin:agent-context {tile}` or `{screen}`: the message box's "About …" chip, sent with the next message as its `context`). The contract is in the template's `API.md` §Workspace mode → The page.

## In the xbin app

The iOS app has the workspace agent as its own chrome around the agent's native view ([native.md](/docs/native.md) §The workspace agent's nodes) — the same two layers as on the web: the conversation is the agent's, everything that grants is the app's, drawn from what xbind answers for an id and sent with the device's own session, which xbind takes as the person's.

- **One button, always in the same place.** The trailing-most item of every panel's bar — Home, a screen, a tile, a terminal, an agent — with the number of things that wait for you because of your agent (its requests, proposed admin changes, tile agents it started that wait for you), or a pause glyph. On an open iPhone Duo it is an item of the vertical bar. Home has a row for it under *Needs you*, with its status in words ("working · 2 tile agents · 2 need you", "idle", "paused") and no count plate of its own: the count is on *Needs you* and on the bar's item. A person without an agent — an admin who gave others one and not themselves included — and any workspace whose xbind has none, sees neither, and a link to the agent then opens the workspace's Home.
- **Beside the work.** On an iPhone the agent opens as a sheet, large first; pulled down to medium, the tile behind it stays usable and the sheet shows the newest lines, the quick replies and the message box (tapping the box raises it again). On an iPad it is a trailing column beside the panels; on an open Duo, the second pane. Opened from a tile, that tile is offered as the message box's "About …" chip — an offer for the next message, one tap to remove; from a screen, the screen.
- **The conversation** is the same as on the web — the plan, questions as choice rows with "Something else", the editable brief, xbin's refusals with the way forward, the empty state with starters that fill the box, sessions, the scope line and its panel (totals, orgs unfolding to tiles, staged ticks and Apply, the model with its what-if, a refused change with a new session as the way forward), the notebook, the banners. A request and a tile agent are cards **the app draws**: the agent's view names an id, and the app reads what the card says from xbind. A tile agent's **Open** (or **Answer**, when it waits for you — only you can) goes to the app's own agent screen for that session. Where the agent hands a request about code to a tile's own agent, the tile's launcher opens and nothing is started — not even with one coding agent there — until you pick one; the text it carries over waits unsent in the new session's message box under the label "Suggested by your agent's page — not your words", until you edit it or press Send.
- **An approval** is the app's own sheet, under a bar that says so ("XBIN · APPROVAL — asking Ana Ruiz"): the tile and your level on it, the exact call, what is sent (text, or "not text", its size and hash), whether it can be undone, and the agent's own words quoted as unchecked. Nothing of a request is ever rendered as markup or a link. **Deny** is on the left and **Allow** on the right, at the bottom; Allow answers only to a tap made at least 600 ms after the sheet is fully shown, with the app in front. The three choices are the web's — once, always this exact action, every change to the tile — and the last opens a second sheet whose primary button is *Go back* and whose *Allow every change* asks Face ID. A tile agent's start leads with its **mode**; one that never asks is said in the danger wording, and *Deny* becomes the primary button. One request at a time: the next that waits shows after a decision, on *Once* and with Allow waiting again. **What widens is armed like Allow**: choosing a standing approval, "Until I take it back" over "For one hour", and in Preferences "Start without asking" and turning the admin opt-in on are dimmed and answer nothing for 600 ms after they show, under another sheet, and while the app is not in front; choosing less is never held. A start's mode is "asks before acting" only where xbind says so (a coding agent's ask or plan mode): any other mode, and one xbind doesn't vouch for, is the danger wording.
- **Admin changes** are a full-height sheet: a card a change, before above after, effects, warnings as prominent as the line; an item with a warning starts unticked, a blocked one can't be ticked. Applying asks Face ID in the app, and xbind's own recent-sign-in rule still stands: where the server asks, the sheet asks for the password (or to sign in again) and keeps the ticks. The results name what was applied, failed, skipped and out of date; **Undo** proposes a new set to review.
- **The shield** in the agent's bar holds xbin's own controls: Needs you, **Approvals** (each with Take back), **What my agent did**, **Preferences** (whether it may start tile agents without asking; for an admin, whether it may propose admin changes — opened from here only: the agent's view can ask the app for Needs you, Approvals and the log, never Preferences), and **Pause my agent** — immediate, no confirmation. While paused, a bar under the message box says so, what it means, and holds **Resume** — the one place that says it: the agent's view draws no paused banner of its own, and never a Resume, because resuming is a grant. Words typed and not sent stay in view in the message box, read-only until Resume (nothing can be sent while paused).
- **Needs you** (the app's inbox) lists the agent's requests and proposed admin changes above the sessions that wait, each with **Review…**; the badges count them. A link to the agent (`xbin://<workspace>/xbin/agent`, or to its component — what an approval's push carries) opens the agent, not a tile screen.
- **In place of the conversation** the app says what xbin says on the web — turned off, no language model, locked after a restart, waiting for a newer xbin — and then who changes that and where (an admin, on the web; whoever runs the workspace). It follows the workspace's switch as it is turned. When xbind can't be reached, a conversation already loaded stays readable under xbin's line ("Can't reach xbin."), and its Review… buttons wait for the connection. A message to an agent that is off is not sent and not queued: the words stay in the message box, and the conversation says which switch is on. An admin before setup sees the three steps, read-only, and **Open the setup on the web**: setup is not built natively.

Face ID is the app's own gate — that it is you holding the phone. It never counts as the server's recent sign-in, and a phone without Face ID, Touch ID or a passcode has no such gate. Not in the app yet: approving or denying from the lock screen, a Live Activity for the agent's tile agents, dictation, Handoff to the dock.

**A native tile cannot draw a grant.** A tile's native view runs as the tile, on its frame token, in a hidden web view that never holds the person's session: xbind refuses that credential every route that decides. The `request` and `session` nodes are drawn by the app, and only in the agent's own container; anywhere else they are an inert line. Only the component xbind names as the person's agent (`agent` of `GET /delegate/state`) may ask the app's chrome anything (`xbin.native.agent`), what it may ask is to *show* something by id, and the app reads what it then shows from xbind — as the dock does for the page.

## For tile authors

A workspace agent's call to your tile's API looks like its person's — `X-XBin-From: user:<id>`, `X-XBin-User`, their level, role `reader` or `writer` and never `admin` — plus **`X-XBin-Agent`**, the sealed component's path.

- **Declare what agents may use.** `"agent"` in the tile's `xbin.json`: `"full"` (the default), `"read"` (agents see what the person sees and change nothing) or `"off"` (the API hands out secrets or is a control surface). A manifest can lower the level at once; raising it needs a person who manages the tile ([protocol/delegation.md §A tile's agent level](/docs/protocol/delegation.md)).
- **Check `Caller.Agent`.** `xbin.Caller(r).Agent` (or `ByAgent()`) is the acting component, empty for the person's own hand. A route that *answers* something a person was asked — an approval, a permission, a question, a consent, a sign-in — refuses a caller with it, whatever the manifest says ([elements.md → A person's agent](/docs/elements.md)).
- **Write an `API.md`.** The agent reads it before it calls your tile: say what each call does and what it changes. It is read as a description, never as instructions.
- **What your tile returns is data.** The agent is told that tile data, logs and pages are things to report, not to obey — but a tile that returns "ignore your instructions" is still a tile behaving badly. Don't put text meant for agents in data.
- **A person approves a call, not a meaning.** xbind shows the method, the path and the body. Make write routes say what they do in their path and body, so the approval a person gives is an informed one.

## What the language model's provider sees

The agent's model calls go through xbind's LLM connector, on the model its session is on. The provider of that model receives the conversation: what the person wrote, the agent's replies, and the results of its tools — tile names and status lines, what a tile's API answered, log lines (redacted for known secret shapes), a tile agent's report, the research sub-agent's summaries, and the notebook pages the session may read. It does not receive tile code unless a research sub-agent quoted a line of it, a tile agent's transcript beyond its final report, or anything from a tile that isn't connected.

Orgs decide which models may see their tiles ([protocol/orgs.md](/docs/protocol/orgs.md)): a session on a model an org doesn't allow isn't connected to that org's tiles, xbind remembers which orgs' data a conversation has read, and notebook pages carry the orgs whose data they may hold — a session reads a page only when its model is allowed by every one of them. A tile agent the workspace agent starts runs on the harness and model the person's preferences and the tile's org allow, with its own sign-in or the connector.

## What the agent knows about xbin

The agent's prompt carries a short map of xbin — components and tiles, screens, people's access, orgs, partitions, grants, interfaces and bindings, sandboxes, terminals, tile agents, and what the agent itself is — generated from these docs by `hack/wsagent-model.sh` (the passages it quotes are listed in `hack/wsagent-model/main.go`), under a size budget, and checked by a test: change a quoted passage and the test fails until the file is regenerated. Everything else it reads on demand, with `docs_search` and `docs_read` over the docs xbind serves.

## The notebook

"What the agent remembers": Markdown pages in the person's own partition, with every version kept. The agent writes what should outlast a session — how the person likes things done (the page `preferences` is shown to it in every session), what their tiles are for, what a research sub-agent verified about a tile (stamped with the tile's revision). The person reads, edits and deletes any page; deleting a page makes the agent forget it. Every page the agent writes carries the orgs whose data its conversation held at that moment, and a session reads a page only when its model is allowed by each of them; reading one marks the session as holding that data. A page closed to a session is still listed for the person, who can edit it; an edit keeps its marks. Nothing clears them in place: to unmark a page, delete it and have a session that holds none of that data write it again.

## Setting it up

The workspace agent ships in xbind and is inert until a workspace admin does three things. Inert means a workspace holds nothing of it but its one data stamp (`data/sealed/wsagent.json`, written at boot so its data key is claimed): no partition mode record, no volumes, no mount — those come with the first person's agent. An admin sees them as one list in xbin's chrome — the **set up workspace agent** chip in the top bar, or `/xbin/agent` — and nobody else sees anything until they are done.

1. **Connect a language model.** `/xbin/llm` ([llm.md](/docs/llm.md)): a provider key, or a model your organisation runs itself. The agent's model slot is bound to xbind's own connector and can be bound to nothing else; it uses the connector's default model (the `agent` role's, where one is set) unless a person picks another that the rules allow. Without a model the agent has nothing to think with: no session can be opened.
2. **Turn workspace agents on.** One switch for the workspace (`PUT /api/xbin/delegate/workspace {enabled: true}`), off by default. While it is off xbind refuses every call any agent makes for anyone. Turning it off again stops every agent at once.
3. **Choose who gets one.** A person has an agent when they have *read* access to the component `xbin/wsagent`, and nobody has that until it is given: a system component is reached only by an access entry that names it, so `*` and other patterns — written about tiles — give nothing here. The chrome offers the two usual choices, **Everyone** (one entry in the workspace's default access) and **Just me for now** (the admin's own entry); the same as `PUT /api/xbin/delegate/workspace {who: "everyone" | "me"}`, and `{who: "chosen"}` takes it back from everyone while leaving the entries people and orgs have of their own. One person or one org at a time is ordinary access: Admin → People → the person's access (or `PUT /api/xbin/access`, `bx access`), an entry for `xbin/wsagent` at `read`; an org shares it to its members the way it shares a tile. Admins read it without an entry, as they manage it. — and that is all the role gives: an admin has an agent of their own only when an entry gives them one (**Just me for now** writes it, **Everyone** covers them). Administering the component and having an agent acting as you are two things.

Each step is checked by xbind when the agent acts, not by the page: a person without access gets no agent, no chip and no notice even while the switch is on; with access and the switch off, their agent can call nothing.

**On a new workspace, one click.** The first time the owner opens the login URL — the bootstrap token's browser session, in a workspace with no accounts yet — xbin's **first-run sheet** makes their admin account, sets up the vault and, where a model is connected (the host's or an admin's), does what is left of steps 2 and 3 for them: its button reads **Create my account and turn on my workspace agent** and, as the new account, sends `PUT /api/xbin/delegate/workspace {enabled: true, who: "me"}` when the switch was never set, or `{who: "me"}` when workspace agents are on already (an admin's switch, or the host's file leaving who to admins) and nobody has one; the shell opens with the agent's dock and its message box ready. Where the host's file gives admins or everyone one, the button just makes the account and the agent is there; where an admin set agents up already, or the host turns them off, it leaves them. **Just me** is the only choice it makes; **Everyone** stays a later, deliberate one. A quiet button makes the account without the agent; with no model the sheet says the agent needs one. A workspace that has any account never sees the sheet ([auth.md §Owner login mechanics](/docs/auth.md#owner-login-mechanics), D236).

### Set by your host

A host can decide this for its workspaces in its deployment file — the LLM connector's (`XBIN_LLM_CONFIG`, [llm.md §The host's file](/docs/llm.md#the-hosts-file-xbin_llm_config)) — with the key `workspaceAgent`, read and locked as the connector's settings are:

```jsonc
"workspaceAgent": false                                 // off, and admins can't turn it on
"workspaceAgent": true                                  // on; who gets one stays the admins' choice
"workspaceAgent": { "enabled": true, "who": "admins" }  // on, and every admin account has one
"workspaceAgent": { "enabled": true, "who": "everyone" }
```

What it sets, xbind keeps in force: the switch (written as the host's, `by: "host"`) and who has an agent — `"everyone"` the workspace defaults' entry, added if it isn't there; `"admins"` an entry for every admin account that has no agent and no entry of its own, given when the key first appears, to each admin made after, and again when people change. xbind records what the host wrote (`data/hostagent.json`) and takes back exactly that: an entry it gave goes when that person stops being an admin or the key stops saying `"admins"`, the defaults' entry it added goes when the key stops saying `"everyone"`. It never removes, lowers or overwrites an entry a person or an admin made, and an entry it gave that someone changed since is theirs. **When the key goes** (or the file), the switch returns to the workspace's own setting from before the host first set it — off, if it had never been set; if the host never had to change the switch, it stays as it is — and the controls are an admin's again. Reads say what is the host's (`locks` on `GET /api/xbin/delegate/state` and `/delegate/workspace`: `{"enabled": {"locked": true, "reason": "set by your host"}}`), a `PUT /delegate/workspace` of a locked key answers 409, and the chrome shows **Set by your host** on those steps, read-only, or says the host turned agents off. A misspelled key stops xbind's boot; a bad change is refused and the last good file stays.

**What a person then sees.** The **workspace agent** chip in the top bar (in a workspace whose shell predates it: one notice that names `/xbin/agent`). The first time they open it xbind starts *their* agent — a backend of their own, in a sandbox, with their conversations and notebook in their own encrypted data — which takes under a second; it stops again after three minutes without use and starts on the next visit, or when something it waits for happens. Their first session, Main, is made then.

**What it costs to run.** One backend per person who is using it: about 60 MiB of memory each when idle and 74 MiB after a long conversation and a compaction (measured), plus the encrypted volumes of their data. Each is capped at 512 MiB — a quarter of a tile's default, and yours to raise as a tile's ([isolation.md](/docs/isolation.md) → Resource limits) — and xbind stops one that sat unused for three minutes: the next visit starts it again in a fraction of a second. At most 32 run at once by default (the partition limits of any per-person tile: Admin → Runtime, `GET /api/xbin/partitions?tile=xbin/wsagent`). It needs sandboxes: on an xbind run without `--isolate` the agent is held and the chrome says so. A development xbind (`--dev`, `--no-auth`) compiles the agent from the checkout the first time it is opened; an install runs the build that came with the release and never compiles.

## Running it

- **Turn it on**: the three steps above — on a new workspace, the first-run sheet's one button; or the host's file ([Set by your host](#set-by-your-host)).
- **Constrain it**: per org — workspace agent on or off, which models, which coding agents ([protocol/orgs.md](/docs/protocol/orgs.md)). Per tile — its `"agent"` level.
- **Watch it**: every side effect, approval and refusal is in the person's log (`GET /api/xbin/delegate/audit`; an admin reads another person's with `?user=`). The agent and its page can't read it.
- **Stop it**: a person pauses their own (`PUT /delegate/state`); an admin turns it off for the workspace. Tile agents already running keep going, as their person's sessions.
- **Its own API** (for the page that shows it, and for debugging): the template's `API.md` §Workspace mode.
