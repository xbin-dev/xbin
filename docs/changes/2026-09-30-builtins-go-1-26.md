# 2026-09-30 — builtins at `go 1.26.0`; the workspace `go.work` follows its modules

## What changed

Two builtins moved their Go dependencies to versions with security fixes
([changelog](/docs/changelog.md)). Those versions need Go 1.26, so their
`go.mod` files now say `go 1.26.0` (was `go 1.24`):

- **`sandbox-terminal` v6**: `golang.org/x/crypto` v0.57.0 (≥ v0.56.0
  needs go 1.26.0). You get it when you update the tile.
- **The agent template**: `golang.org/x/text` v0.42.0, `golang.org/x/sys`
  v0.48.0, `modernc.org/sqlite` v1.60.1. A new agent instance gets them. An
  existing one gets them when it merges the template update.

The workspace's generated `go.work` used to say `go 1.24` always. It now
says the highest `go` line among `1.24` and the modules it uses. That is
the root one terminals, editors and gopls use, and a restricted terminal's
filtered copy. The go command refuses a `go.work` whose `go` line is below
a module it uses, for every command: `go: module ./apps/x listed in
go.work file requires go >= 1.26.0, but go.work lists go 1.24`. So under
the old rule, a single tile at `go 1.24.0` or later stopped every `go`
command in every terminal. `go mod init` writes `go 1.24.0` on the old
base. An open restricted terminal's `go.work` is now rewritten as the
workspace changes, where before it was fixed when the terminal opened.

The base rootfs ships Go 1.26.3 (was 1.24.0).

## Who's affected

Once any Go module in the workspace says `go 1.26.0` or higher, so does
the root `go.work`. That happens when you update to `sandbox-terminal` v6,
create an agent, or merge the agent template update. It also happens when
you `go mod init` a tile on the new base, which writes `go 1.26.3`. From
then on:

- **Terminals on an older base** (built before this release; Go 1.24.0),
  **only where an admin turned base auto-update off.** With it on, the
  default ([changes/2026-10-01-base-auto-update.md](/docs/changes/2026-10-01-base-auto-update.md)), a terminal
  moves to the Go 1.26.3 base by itself at its next start: the upgrade
  restarts xbind, which ends every session, so that is the first one
  opened after it (a shell's, or an agent session's). Its first line, in
  grey, says the move reset everything outside the workspace files and
  `$HOME` — installed packages, `/etc`, `/var`, `/opt`…, a VM terminal's
  whole disk; files and `$HOME` are kept. With it off, every
  `go` command in such a terminal, for any tile, first downloads that
  toolchain (`GOTOOLCHAIN=auto`):

  ```
  go: downloading go1.26.0 (linux/amd64)
  ```

  A terminal whose network scope can't reach `proxy.golang.org` fails
  instead. That includes `none`, and a network set that is LAN-only or
  names other destinations:

  ```
  go: download go1.26.0 for linux/amd64: toolchain not available
  go: download go1.26.0: golang.org/toolchain@v0.0.1-go1.26.0.linux-amd64: Get "https://proxy.golang.org/…": dial tcp: …
  ```

- **A downgrade to an xbind released before this one** (v0.3.64 and
  older). Those releases write `go 1.24` into the root `go.work` and build
  every Go tile with it. So **every** Go tile's build fails there, not only
  the updated ones, with `go: module ./apps/sandbox-terminal listed in
  go.work file requires go >= 1.26.0, but go.work lists go 1.24`. A tile
  whose `go.mod` says `go 1.24.0`, as `go mod init` on the old base wrote,
  already did this before.
- **A host whose Go is older than 1.26.0.** xbind builds tiles with the
  host's Go, which downloads go1.26.0 for these builtins' builds, or fails
  with `GOTOOLCHAIN=local`. A host the installer set up has Go 1.26.3 or
  newer.

Unaffected: terminals on the current base (with base auto-update on,
every terminal from its first start on this release), tile builds on
installer-made hosts, and workspaces where no module says more than `go
1.24`.

## How to migrate

1. **A terminal on an older base:** nothing, while base auto-update is on
   (the default): its next session starts on the current base, with Go
   1.26.3. To keep what the terminals' layers hold instead (installed
   packages, `/etc`, `/var`…), an admin turns it off before any session
   starts on this release — so before upgrading: write
   `{"baseAutoUpdate": false}` to `data/workspace-settings.json` in the
   workspace (an older xbind ignores the file). On a running xbind, `bx
   settings set --base-auto-update=false` on the host, or the admin
   console's workspace → terminals tab (an admin tile updated with `bx
   builtin update`), sets it for the layers not moved yet. With it off, click **⬆ base
   update** in the window's title bar, or in the "Start a session in …"
   chooser, when you are ready. The terminal's layer is rebuilt on the
   current base, with Go 1.26.3. This
   wipes packages you installed (apt). Your workspace files and `$HOME`
   are kept. Or keep the old base and let `go` download go1.26.0 once
   into the module cache in your `$HOME`. That needs `proxy.golang.org`
   and `sum.golang.org` in the terminal's network scope, which a terminal
   that downloads Go modules reaches already.
2. **Before downgrading below this release:** on the host, set the `go`
   line of every `go.mod` in the workspace that says more than `go 1.24`
   back to `go 1.24`. To list them, run this from the workspace root:
   `grep -rH --include=go.mod --exclude-dir=homes --exclude-dir=data --exclude-dir=.xbin '^go ' .`.
   The older xbind's `go.work` then accepts each module, and the host's Go
   (1.26.3 or newer) still builds the dependencies that need 1.26. After
   upgrading again you can leave them: this release builds such a module
   too, and `go mod tidy` restores the line.
3. Nothing else: tile builds on this release choose their modules
   themselves (D166) and are unaffected.

## Why

The builtins' old dependency versions carried vulnerabilities their code
reaches. Ten were in `golang.org/x/crypto/ssh` under `sandbox-terminal`'s
SSH server. One was in `golang.org/x/text` under the agent's JS engine. The
fixed versions need go 1.26.0 (x/crypto) and 1.25.0 (x/text). Before D166,
the shared `go.work` lifted every tile to the newest version any tile
required, which partly hid these old versions. Each tile now builds with
its own `go.mod` ([D166](/docs/changes/2026-09-30-go-build-workspace.md)),
so the fixes have to be in the builtins themselves. A security fix ships in
the release that finds it ([compat.md](/docs/compat.md) rule 11).

A `go.work` that says less than its modules breaks every `go` command, so
its `go` line has to follow them. The coding-sandbox template reaches no
vulnerability and stays at `go 1.24`, so it has nothing to merge.
