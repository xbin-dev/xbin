# 2026-10-03 — Base Two: what a tile from before the theme sees, and how to keep its look

## What changed

The workspace draws in Base Two (D184): Concrete Night (dark) and Concrete
Day (light), following the person's system setting unless they pick one
in Settings → Theme. `/vendor/theme.css` carries both. A document follows
the person only when it opts in with `<html data-bx-theme="auto">`; every
other document that links the sheet gets Concrete Night, as it got the
dark-steel palette before ([frontend-kit.md](/docs/frontend-kit.md)
§Theme, [compat.md](/docs/compat.md) rule 5).

A tile from before Base Two that links `theme.css` and never opts in sees:

- **Night's colours under the same names** — `--bx-bg`, `--bx-panel`,
  `--bx-panel-2`, `--bx-border`, `--bx-text`, `--bx-muted`, `--bx-accent`
  (now periwinkle, `#8C9BFF`, was amber) — and new tokens beside them.
- **The old status names keep their old values**: `--bx-green` `#4CAF50`,
  `--bx-amber` `#F2A71B`, `--bx-red` `#EF5350`, so white text on a fill of
  one reads as it did. The core elements' status colours (`--bx-ok`,
  `-warn`, `-danger`) follow them in such a document.
- **New faces and type**: `--bx-font` is Instrument Sans at 13/18
  (`--bx-mono` JetBrains Mono, served from `/vendor/fonts/`), corners are
  2 px (`--bx-radius`), shadows are new.
- **`.bx` controls restyled, not resized**: a `.bx button` is weight 600 on
  a `--bx-border-strong` edge with 4×11 px padding, fields sit on the panel
  with the same edge, and every interactive `.bx` element shows the focus
  ring (3 px cyan over a 2 px gap) on `:focus-visible`. `button.primary`,
  `.quiet`, `.danger`, `:disabled` and the 28 px minimum size are **not**
  applied: they wait for the opt-in, and are written at the base rule's
  specificity, so a tile's own classes of those names win.
- **A palette of its own carries**: a tile that set the old names in its
  own `:root` rule (a light palette, say) gets the roles Base Two added on
  top of them computed from its values — the button hover, the code well
  of a `<bx-code>`, the tints of a `<bx-dialog>`'s error line, the
  accent's hover and the ink on it, links, window chrome — as the same
  rules followed its values before. Base Two's own values for a few roles
  don't follow it (below).
- The person's theme choice changes nothing in it: the injected
  `<meta name="xbin-theme">` is read only by documents that opt in.

A document that never linked `theme.css` is unchanged: the core elements in
it draw Night from their fallbacks.

The scaffold (shell, root page, admin console, manager, API docs,
organisations, welcome) takes Base Two when its units are updated, one at a
time: `bx builtin update scaffold:root`, `scaffold:shell`,
`scaffold:tiles/admin`, `scaffold:tiles/manager`, `scaffold:tiles/apidocs`,
`scaffold:tiles/organisations`, `scaffold:apps/welcome`.

## Who's affected

- Tiles that link `/vendor/theme.css` with `<body class="bx">` and style
  themselves on the tokens: they look like Concrete Night now — the same
  layout, new colours and faces.
- Tiles that set the old token names for a palette of their own: the
  roles above follow; a `<bx-code>` in such a tile shows plain code on the
  tile's own background, but its syntax and diff colours are Night's
  (they were a fixed One Dark palette before, no better on a light page).
- Tiles that relied on a `.bx button`'s old 12 px type or 3×10 px padding
  for a tight layout: buttons are a little larger (13/18 type).
- Workspaces that update only `scaffold:shell`: the root page stays dark
  and the new shell shows Theme and Density disabled until
  `scaffold:root` is updated too.

## How to migrate

Nothing has to change. To keep a look exactly, or to take Base Two:

- **Take the theme** — add `data-bx-theme="auto"` to your `<html>`, keep
  the `theme.css` link, and look at the tile in both themes (the system's
  setting, or Settings → Theme). Fills: a `-bg` tint (`--bx-ok-bg`, …)
  with the status colour or `--bx-text` on it — in Day the old names are
  dark text colours, so a fill of one needs white text. The variants
  `button.primary`, `.quiet` and `.danger` come with the opt-in.
- **Keep your own palette** — set it in your own `:root { … }` after the
  `theme.css` link, as before. Besides the old names, set what you want
  your own of the roles that don't follow them: `--bx-selection` /
  `--bx-selection-text`, `--bx-focus` / `--bx-focus-gap`, `--bx-subtle`
  (placeholders), `--bx-border-strong`, and for a `<bx-code>` on a light
  page the `--bx-syn-*` and `--bx-diff-*` colours
  ([frontend-kit.md](/docs/frontend-kit.md) §Theme › A palette of your
  own lists them all).
- **Keep the old faces** — set `--bx-font` (and `--bx-mono`) in your
  `:root` rule to the stack you had (`13px/1.45 -apple-system, "Segoe UI",
  system-ui, sans-serif` was the default).
- **Keep old dense buttons** — your own `button { … }` rules win over
  `.bx button` only with the same or higher specificity: write them as
  `.bx button { font-size: 12px; padding: 3px 10px; }` after the link.
- **Update the scaffold** with the unit ids above; customized units merge
  (`--merge`, or `--pr` for a proposal).

## Why

The workspace had one dark palette and nothing that let a person read it
in light; Base Two gives every shipped page both themes, a per-person
choice and a guard that keeps colours on tokens. A document turns light
only when it opts in because third-party tiles hard-code text colours for
the dark palette they were written against: switching them would have
broken their legibility. The old names keep their old values in those
documents for the same reason — white text on `var(--bx-green)` was the
examples' own pattern — and the roles that sit on the old names are
computed from them so a tile's own palette keeps working with the core
elements it embeds.
