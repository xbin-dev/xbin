# B1 — coding-sandbox partition keying: records for the integrator

Branch `pt/b1`. Implements PD-39 (with the provider rule of PD-14 and the
wire key of PD-43), closing C7, C11 (manager side), C12 (manager side:
the capability), S14 and S19 for sandbox managers. No `rehome`.

## docs/changelog.md entry (fold under the merge date)

- **Sandbox managers key partitioned consumers per person**
  ([sandbox-manager.md](/docs/sandbox-manager.md) §Partitioned consumers, D<n>).
  A manager whose `hello.caps` carry the new `partitions` capability (the
  manager's own — never in a sandbox's `caps`) takes a partitioned
  consumer's calls as (`X-XBin-From`, `X-XBin-Partition-Id`): a sandbox
  made in a person's user partition is homed there (`owner.partitionId`,
  `owner.partition`) and invisible to the consumer's global instance, its
  other partitions and every other consumer unless shared (`shares` gain an
  optional `partitionId`); the partition's person is verified (an `Sbx-User`
  or `X-XBin-User` naming anyone else is `403 not-allowed`); a partition
  also sees what its person may use at the consumer's non-personal identity,
  never the converse. An absent partition and `global` are one consumer, so
  every existing sandbox stays with its consumer's global instance.
  `clientId`s are per partition; quotas per consumer count all its
  partitions. The builtin **coding-sandbox** template does all of it, tells
  the runtime the partition as the label `coding-sandbox/partition`, and
  shows its operators a user partition's sandbox as `<consumer>/<partition
  id, 8> #<n>` without labels unless it is shared with them. The
  conformance suite (`sdk/sandboxcontract`) gains a `user-partitions`
  section (run when hello offers `partitions`), `Target.Partition`, and
  `Caller.InPartition`/`Global`; `hack/fakesandbox` follows (without
  `partitions` in its `Caps` it behaves as a manager from before them).
  Nothing changes for an unpartitioned consumer; existing copies of the
  template take it with a template update.

## plans/DECISIONS.md entry (D-number at merge, PD-41)

- **D<n> — Sandbox managers key a partitioned consumer's user partitions
  (the partitioned-tiles plan's PD-39; 2026-09-29).** Extends D115's
  contract (protocol 1, by addition: a capability, two optional fields) and
  D122's builtin manager. docs/sandbox-manager.md §Partitioned consumers;
  coding-sandbox API.md; plans/partitions/09 §1, 07 §4.
  - **Chosen.**
    - **Consumer = (From, partition id).** The id is
      `X-XBin-Partition-Id` (the opaque pkey of PD-43, so a recreated
      person never inherits records — C11) and `""` for the consumer's
      non-personal identity, `global` included (S14: every sandbox made
      before the consumer turned partitions on stays its global
      instance's). Not keyed on `X-XBin-Deployment`: user partitions are
      primary-only (PD-17) and keying today's non-primary deployments apart
      would strand the sandboxes they made (see the deviations below).
    - **The person from the partition.** A user partition's call is
      verified as its person; `Sbx-User`/`X-XBin-User` naming anyone else
      is 403, and so are partition headers that don't agree (a user
      partition without its id, an unknown kind) — fail closed, never read
      as global.
    - **Global-home visibility (C7).** A user partition sees what its
      person may use at the consumer's non-personal identity — a sandbox
      homed there, or shared with it, where `personOK` passes (team, owner,
      member, a share's `users`) — so the agent page's direct terminal
      dial keeps working for shared conversations. Such a sandbox reads
      `shared: true`; the partition can't change who uses it or delete it.
      Anything else of the consumer's stays `not-found`. Never the
      converse. (The plan spoke of global-home records; shares with the
      consumer's non-personal identity follow the same "what the person
      could see at global" rule.)
    - **`hello.caps` gains `partitions`** — the plan's `caps.partitions: 1`;
      `caps` is a list of words in protocol 1, so the capability is the
      word (the contract grows by addition: new capabilities). It is the
      manager's, never a sandbox's; consumers (the agent, B2a) and xbind's
      switch confirmation / `bx doctor` (F13a/F11) test for the word.
    - **Operators (S19).** Metadata as before; a user partition's sandbox's
      name and labels are shown as `<consumer>/<partition id, 8> #<n>` and
      none unless shared with the viewing operator (they could use it as a
      consumer). The runtime keeps `for` = the tile and gets the partition
      id as the label `coding-sandbox/partition` (the plan's "ForPartition
      label"; no SDK/tilesbx field was added).
    - **Quotas** per consumer sum every partition of the tile; per person
      as ever. `clientId`s (create, exec, snapshot) are per (consumer,
      partition); global's stored keys are byte-identical to before.
    - **Conformance suite.** A `user-partitions` section gated on the
      capability: partitions apart, `""` ≡ `global`, global-home records by
      the person rules, shares to (consumer, partitionId), a mismatched
      person refused, a recreated user (new id) sees nothing of the old.
      The consumer-level `partitions` section is unchanged. The live
      isolated run (test/isolated) skips it until a partitioned consumer can
      be driven through xbind (xbind strips the headers the suite sets).
    - **hack/fakesandbox** implements the same; with `Caps` lacking
      `partitions` it ignores the headers — the old-manager fixture for the
      agent's degrade path (B2a). Its mirrors follow; sandbox-terminal v3.
  - **Not chosen:** a top-level `hello.partitions: 1` (a second way to say
    a capability); keying on `X-XBin-Deployment` too; redacting snapshot
    names on the operators' routes (the plan names sandbox names and
    labels only — a follow-up if wanted); a `rehome` route (PD-34).

## Deviations from the plan (also in the pack report)

1. `caps.partitions: 1` → the word `"partitions"` in `hello.caps` (caps is
   a string list in protocol 1). Consumers/xbind check
   `caps.includes("partitions")`.
2. The pack line says "(From, Deployment, Partition)"; 09 §1 / 07 §4 say
   (From, partition id). Implemented (From, partition id) — Deployment is
   not keyed (today's behaviour for non-primary deployments is kept).
3. "ForPartition label" is the runtime label `coding-sandbox/partition`,
   not a new `SandboxSpec` field (no SDK / internal/tilesbx change).
4. C7 visibility is generalised to shares with the consumer's
   non-personal identity (documented in the contract).
