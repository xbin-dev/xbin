## Bugs found

None in xbind: every attempt the suites make — the review fixes' new ones
included — answered as designed. Four of the first implementation's
expectations were wrong and were corrected against the design, not the
code:
- an admin lists personal-bind *records* (PD-54's hygiene exception);
- an admin's consent (`POST /partitions/consents` in their own session)
  is their own, never another person's;
- the root token decides a mode (owner is admin; `modeDecider` accepts
  `p.Owner`) — tile credentials never do;
- a partition asserting another person at the sandbox manager is `403
  not-allowed` ("a call from user:bob's partition acts for bob, not
  alice"), not 404.

**Looks wrong (F11's, UI, not fixed):** on the partitions page, after
**Allow** on an asked card the new consents-table row shows the Allow's
answer ("Allowed: … may use your data in …") where **Take back** goes,
until the page re-reads its model (a reload): the asked card and the row
share the UI key `consent:<from>→<to>` (`web/partitions-more.js`
`askedCard`/`consentTable`). A person can take it back after a reload.
The `personPageAsked` pass reloads before taking it back and says why.

**Not an isolation need:** F11's record says the asked consents need a
refused call between running partitions (isolation). They don't: a
frame's resource read through another tile's grant is refused and asked
without any backend — `personPageAsked` drives it on the default,
unisolated harness.

## Owner questions

1. **Run the whole `user-partitions` section through xbind?** Four of its
   six checks can't: they call a partitioned consumer without a partition
   as a verified person, or have a partition verify another person —
   callers xbind never makes — or use the suite's synthetic partition ids.
   A small additive hook in `sdk/sandboxcontract` (say `Target.PartitionID
   func(person string) string` for the ids, and the four checks' non-xbind
   callers moved behind a "direct" flag the xbind target turns off) would
   let them run. It changes a builder-facing package (docs/sandbox-manager.md
   and a changelog line). **Recommendation:** yes, as a B1 follow-up; until
   then the declared skips plus `user-partitions-xbind` cover what xbind can
   send, and the in-process run covers the rest.
2. **llm-gw's recreated person** (W4-wire): a person deleted and made again
   under the same id keeps seeing their old partition's usage row until
   their new partition calls llm-gw once — xbind tells tiles of no deletion.
   **Recommendation:** accept (usage counters, a manager's view; the row
   goes at the new partition's first call); a `partitions` event op for a
   deleted partition, sent to the tiles it used, is a later, general
   feature if other providers need it.
3. **xbind's data plane on a person's partition without `--isolate`.** On
   a non-isolated xbind a person's partition never runs (PD-19: the
   backend answers 503 "the partition can't run: a person's partition runs
   only in a sandbox (--isolate)…"), but xbind's own resource API still
   serves their frame their own partition's namespace: a PUT to
   `/api/xbin/kv/res:<tile>/kv/<key>` is 200 and lands in
   `data/resources-enc/.partitions/<scope>/main/<pkey>/` — theirs alone
   (another person and the root token read 404), and a switch deletes it.
   No one else's data is reachable, so it isn't a leak; it is data a person
   writes to a partition that can't run here. **Recommendation:** accept
   and say so in docs/partitions.md's isolation paragraph (a person's
   frame keeps their own data through xbind's API; their code runs only
   under `--isolate`) — refusing it would also refuse the frame-only tiles
   (no backend) that work without isolation today. The alternative is the
   backend's 503 on the data plane too. `TestPartitionsNoIsolate/
   global-only` pins today's answer either way.
4. **The isolated suites in CI.** CI's integration job has no rootfs, so
   the security suite, the smokes and the downgrade SKIP there
   (§Where these run). CI already builds a small Ubuntu rootfs for the VM
   tests; the partition suites also need gocryptfs, fuse-overlayfs and
   unprivileged user namespaces on the runner. **Recommendation:** list
   them in I2's release checklist now (the commands above), and make a CI
   job with a rootfs and the helpers a separate infra change — it would
   cover every `test/isolated` suite, not only partitions'.
