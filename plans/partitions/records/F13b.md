# F13b — records for the integrator

Work pack F13b (templates and updates never switch a mode), branch
`pt/f13b`. Implements **PD-52** and the instantiation half of **PD-35**
(the default and its opt-out, gated by **PD-19**); the design is
plans/partitions/01-manifest-registry.md §2.7. The agent template's own
manifest is **not** flipped here (B2a does that when the agent can run
partitioned). Fold the two texts below into `docs/changelog.md` and
`plans/DECISIONS.md` (the D number is the integrator's to assign).

## docs/changelog.md entry

- **Partitioned tiles: templates and builtin updates never switch a
  partition mode** ([partitions.md](/docs/partitions.md) §The mode,
  [protocol.md](/docs/protocol.md) `/templates`, `/templates/new`,
  `/builtins/update`, [bx.md](/docs/bx.md), [elements.md](/docs/elements.md)
  §Manifest). A template's `"template": {"partition": [...]}` is the mode
  its **new** instances start in: instantiating writes it as the copy's own
  top-level `partition`, and the fresh instance's mode is recorded at once,
  naming who created it. Opt out per instance with the Tile Manager's new
  **Keep each person's data apart** box on the template card, `bx template
  new <source> --no-partition`, or `"partition": false` in `POST
  /api/xbin/templates/new`; without `xbind --isolate` the default isn't
  written (the box is off, "needs --isolate"). `GET /templates` items gain
  `partition` and `partitionSkipped`, and the instantiation's answer
  `partition` or `partitionSkipped` — all absent for templates that name no
  mode. `bx builtin update` (replace, merge and PR proposals) now keeps each
  `xbin.json`'s **installed** `partition` — present, absent or its list,
  spliced in place with its comments kept — and `POST /builtins/update`
  answers `notes` (and `bx` prints them) where upstream asks otherwise:
  `partition kept as installed (…; upstream asks …): edit it deliberately
  to request a switch`. No shipped template or builtin names a mode yet, so
  nothing changes today. Existing workspaces get the template-card box with
  `bx builtin update scaffold:tiles/manager` (the API and `bx` work without
  it). Nothing to change.

## plans/DECISIONS.md entry

- **D&lt;next&gt; — Partitioned tiles, F13b: templates and updates never
  switch a mode (2026-09-29).** Implements PD-52 and the instantiation of
  PD-35 (gated by PD-19) of plans/partitions/90-decisions.md; the design is
  plans/partitions/01-manifest-registry.md §2.7. docs/partitions.md §The
  mode, docs/protocol.md (`/templates`, `/templates/new`,
  `/builtins/update`), docs/bx.md, docs/elements.md.
  - **Chosen.**
    - **The default lives in the stripped block.** `builtins.InstanceOpts`
      rides `CopyTree`/`RenderTree` (their `stripTemplate bool` became
      `tpl *InstanceOpts`, nil for an import): `stripTemplateBlock` writes
      `template.partition` as the copy's top-level `partition` when
      `Partition` is set, and removes any top-level key when it isn't (the
      opt-out and "no isolation" both mean *no mode at all*). The strip
      keeps its re-marshal (pre-existing: comments dropped, keys sorted), so
      the key lands in sorted order. `TestTemplatesNoTopLevelPartition`
      holds that no builtin template carries a top-level `partition`, which
      is what makes a `git merge template/main` unable to bring one in.
    - **The request.** `POST /templates/new` takes `partition` (only
      `false` means anything: `true` or absent is the default); the broker
      decides `InstanceOpts` in `templatepartition.go` (`instanceOpts`):
      opted out → "opted out", `!confine.Isolated()` → "needs --isolate"
      (`templatesIsolated`, a var tests pin). The catalog shows builtin
      defaults as written (`TemplateEntry.Partition`) and workspace defaults
      through `registry.ParsePartition`.
    - **`by` on the auto record.** The handler notes the instantiating
      person (user id; `owner` for the root token; the component for a tile
      principal) under root+tile in a package-level `sync.Map` for the
      request's duration; F1's `decide` calls `stampAutoBy` (one line),
      which names them on the `auto` history entry the settle adds — the
      watcher's rescan and the handler's own both see it.
    - **Updates splice, never re-marshal.** New `internal/jsonc/members.go`:
      `TopLevel`, `SetTopLevel` (replace in place; absent → before the
      first member, at its indent) and `DeleteTopLevel` (a member alone on
      its line takes the line; the last member takes its separator) edit one
      top-level member and keep every other byte. `ApplyReplace`/
      `ApplyMerge` (now returning `builtins.Applied{Files, Notes}`; the old
      bodies are `applyReplace`/`applyMerge` with a notes sink) write each
      manifest with the installed value. The recorded base stays upstream's
      own rendering, so a kept difference reads as the builder's edit
      (`user`), never as a pending update.
    - **Merges.** When ours, base and theirs agree on `partition`, the
      merge runs as before (the line doesn't move). When they don't, the key
      is taken out of all three, the merge runs, and ours' value is put back
      — so its lines never conflict and upstream's never ride in; beside
      conflict markers it is inserted textually right after the opening
      brace (`insertFirst`), so resolving either way keeps it.
    - **Proposals (`--pr`).** The series' "to" side carries the base's
      value, so the patch never touches the key; the message says what
      upstream asked.
  - **Not chosen:** writing the default at the template's top level (a
    `git merge template/main` would add or remove it); refusing
    instantiation of a template with an invalid default (the instance
    carries it as written and runs no backend until fixed, as F1 does for
    any invalid request); re-marshalling the updated manifest (drops the
    builder's comments); refusing an update whose installed manifest doesn't
    parse (it would block the repair; the note says so instead).

## Deviations and open ends

- **Placement moves on a disagreeing merge.** Ours' `partition` comes back
  as the first member when the sides disagreed (removed, merged, re-added),
  so the line may move within the builder's file; the value never changes.
- **No installed manifest = an install.** A unit whose `xbin.json` isn't in
  the workspace (a MISSING essential tile, a deleted file restored) gets
  upstream's value: there is nothing installed to keep, and F1's gate
  pauses a tile that holds data anyway.
- **An installed manifest that doesn't parse** can't be read for its value:
  replace writes, and merge merges, upstream's file as before, with a note
  ("…doesn't parse, so its partition couldn't be carried over (upstream
  asks …): check the key"); F1 holds a recorded tile whose manifest doesn't
  parse, and a pending request pauses one that holds data.
- **A proposal whose only upstream change is `partition`** now renders an
  empty series and answers "update produced an empty diff": use replace or
  merge (which record the new base with the key kept).
- **A workspace template whose default is invalid** shows no `partition` in
  the catalog (no box in the Tile Manager); its instances still carry the
  value as written. `partition: true` without isolation is not an error: the
  answer's `partitionSkipped` says "needs --isolate".
- **The Tile Manager's Updates tab** doesn't show the notes (it re-renders
  the list at once); the API answer and `bx builtin update` do.
- **UI harness:** no pass covers the template card; the change was checked
  with `make js-check` only.
