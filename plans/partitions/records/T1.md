## What the history shape allows (the analysis)

- **An existing instance's merge base is fixed.** An instance's repo is the
  template snapshot it was seeded from (the template's own JSONC, block
  and comments included — older xbinds mirrored the template's files
  verbatim) plus one "instantiate" commit holding the re-marshalled
  manifest (`json.MarshalIndent`: no comments, keys sorted, every entry
  spread over lines). `git merge template/main` diffs from the last
  snapshot the instance has — whatever the served repo does later, the
  base stays that JSONC, and "ours" is a full rewrite of it.
- **So no form of the served repo makes that merge clean by lines.**
  Checked with the real manifests (pre-B2a `bf5a56b1`, today's): with the
  served manifest in the same normalized form the instance has (theirs =
  MarshalIndent of today's manifest), `git merge-file` still leaves two
  conflicts — exactly B2a's additions, each an empty "ours" against
  upstream's lines, because both sides rewrote every base line. The served
  repo's bytes only choose which conflicts appear; any upstream manifest
  change conflicts in a re-marshalled instance.
- **What does work is a merge that doesn't go by lines.** Parsed as JSON,
  the three sides are plain: upstream added `partitionMail`,
  `partitionNote` and two `uses` entries; the instance changed none of
  them. So the fix is a **merge driver** (gitattributes(5)) for the
  instance's `xbin.json`, which xbind names in each instance's own
  repository, plus **instantiation that stops re-marshalling**, so new
  instances merge line by line anyway.

## What was built

1. **`internal/manifestmerge`** — a three-way merge of a manifest by keys
   (`Merge(base, ours, theirs, Options{From, To})`):
   - objects merge member by member, arrays element by element (an element
     is known by its `target` when it is an object with one — a `uses`
     entry — else by its whole value); a value both sides changed merges
     inside when all three are objects or all arrays, else it is a
     conflict (`*ConflictError` naming it);
   - top-level `template` and `partition` (any case) are **never** taken
     from upstream (the block never reaches an instance; the mode changes
     only by a deliberate edit — PD-52's rule, as `undoPartition` keeps it
     for builtins);
   - the instance's own-path rename (instantiation's `apps/agent` →
     `apps/my-agent`) is applied to the base and upstream first, when the
     instance carries its path, so upstream's new entries arrive with the
     instance's resource names;
   - the result is **ours edited in place** (tree.go keeps every value's
     offsets): untouched bytes stay; what comes from upstream is written the
     way ours is — upstream's own lines re-indented, its comments with them
     (a JSONC instance), or the two-space `MarshalIndent` form with a new
     key where MarshalIndent sorts it (a re-marshalled instance). An
     entry dropped takes its lines and the comment above it; commas are
     put right (trailing-comma style kept). An unedited old instance merges
     to **exactly** today's template instantiated the old way.
2. **`bx template merge-manifest [--marker-size N] [--rename FROM=TO] BASE
   OURS THEIRS`** (cmd/bx/templatemerge.go) — the driver: git's own line
   merge first (`git merge-file -p`; clean → it stands, byte for byte), by
   keys only where that conflicts; it says on stderr what it took. When it
   can't, it leaves OURS untouched and exits 1.
3. **The driver in each instance's repo** (internal/broker/
   templaterepo_driver.go): `merge.xbin-manifest.name/driver` in
   `.git/config` and `/xbin.json merge=xbin-manifest` in
   `.git/info/attributes` — nothing tracked, nothing a merge carries — at
   instantiation (`AddTemplateRemote`) and, for the instances older xbinds
   made, **at start** (`EnsureTemplateMergeDrivers`, after
   `EnsureComponentRepos`). The command is `bx template merge-manifest
   --marker-size %L [--rename <default path>=<instance path>] %O %A %B ||
   git merge-file --marker-size=%L -L ours -L base -L theirs %A %O %B`:
   **without bx (or with an older bx) the merge is git's own**, conflict
   markers included — never worse than before. Both writes run confined
   (one `sh -c` per instance, D78); xbind reads the repo's config and
   attributes only through `fsutil.OpenBeneath` to see whether the
   instance is one and already has the current command (a start with it
   in place spawns nothing).
4. **New instances keep the template's JSONC** (internal/builtins/
   templatestrip.go): the `template` block is spliced out **with the
   comment lines right above it** (they describe the template — "A
   TEMPLATE component … the block is stripped"; `jsonc.DeleteTopLevelNoted`,
   new), the instance's `partition` (when written) goes on the **line after
   the opening brace** (no upstream change sits next to it), every other
   comment and the key order stay. A manifest the splices can't handle
   falls back to the old re-marshal. The served repo (W3b's
   `repoManifest`, for a repo this xbind creates) drops the same comment
   lines, so **a new instance's manifest is the served one plus one line**
   and later template changes merge line by line even without the driver.

**For an unpartitioned existing instance** the merged manifest gains
B2a's `partitionMail`, `partitionNote` and the `conf`/`team` uses — decided:
**they arrive.** They are inert unpartitioned (xbind rings no mailbox, the
note shows only on a mode switch, the code never opens `conf`/`team`), the
`conf`/`team` resources arrive with the merged `scope.json` anyway (a plain
line merge, as before), and the instance then equals a fresh
`--no-partition` instance of today's template — so switching it later
needs only its `partition` line (W3b's "add the conf and team lines…"
advice becomes unnecessary). It never gains `partition` or the block: the
mode stays (checked end to end: unpartitioned, backend in `legacy` mode).

## Deviations

- **The fix is a merge driver plus a new instantiation form, not a
  change to the served repo's form** (the analysis above: no served form
  makes an existing instance's merge clean).
- **Instantiation writes the template's JSONC**, no longer the
  re-marshalled manifest: comments and key order kept, the comment lines
  introducing the block removed, `partition` on the first line. Builders
  see comments in new instances' manifests; nothing reads the manifest by
  bytes (registry, updater and tests read JSONC).
- **The fallback's conflict markers say `ours`/`theirs`**, not `HEAD` /
  `template/main` (the placeholders naming them, `%X`/`%Y`, need git ≥
  2.44; the rootfs's may be older), and ignore `merge.conflictStyle`.
- **The driver covers builtin template instances only** (those with the
  `template` remote); a workspace template's instances have no served repo
  to merge from.
