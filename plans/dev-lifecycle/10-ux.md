# 10 — UX: terminal window, shell, bx, agents

> Status: live — every surface, control, confirmation and string through which people and agents see and operate live reload, tile deployments and promotion (part of [plans/dev-lifecycle](README.md))

This document turns the model ([05-model.md](05-model.md)) into surfaces. It
owns placement, states, controls, confirmation text, the wording table, `bx`'s
human-facing behaviour, the agent guidance text and the harness hooks. It does
not own:
- the wire ([11-contract.md](11-contract.md)): endpoint names, fields and event
  shapes below are proposals that document may rename, but not re-mean;
- runtime behaviour ([07-runtime.md](07-runtime.md)), data
  ([08-data.md](08-data.md)) or the fabric ([09-fabric.md](09-fabric.md)).

Vocabulary is [01-glossary.md](01-glossary.md), verbatim. Facts about today
come from [research/ui-surfaces.md](research/ui-surfaces.md) unless another
research file is named, and every `file:line` was re-checked in this worktree.

Examples use tile `apps/crm`, deployments `main` (the primary) and `dev`,
checkpoints `c:3f2a1c9` (what main runs), `c:7b19e02` (a fresh checkpoint of
the work tree) and `c:1e9d0aa` (an older one), and the user `ana`.

## 1. Principles

1. **The terminal window first.**
   - `web/` is embedded in the binary (`assets.go:11`) and served under
     `/vendor/` with `Cache-Control: no-cache`, because "vendor changes on
     upgrade" (`internal/server/static.go:601`). bx-frame, frame-titlebar,
     frame-launcher, bx-logs, bx-dialog and bx-menu therefore reach every
     workspace at its next xbind upgrade.
   - The scaffold (shell, menus, tile admin, the admin tile) is copied once by
     `xbind init` and changes only through `bx builtin update`
     ([/docs/compat.md](/docs/compat.md) rules 2 and 4). bx-terminal's own
     comment names the trap (`web/bx-terminal.js:261-265`).
   - So every state in §12.1 must be visible, and every operation in §5 must be
     reachable, from the terminal window alone. A workspace that never runs
     `bx builtin update` has the whole feature.
   - New UI goes into new `/vendor/` siblings: `web/bx-frame.js` is at 866 of
     its 900-line cap, and frame-titlebar and frame-launcher were extracted for
     exactly that reason (`web/frame-titlebar.js:2-4`).
2. **Scaffold surfaces are garnish.** A card chip, sidebar badge, tile-menu
   line or admin row (§7):
   - must render nothing when the field it reads is absent (an older xbind);
   - must never be the only path to anything;
   - follows the shell's pure-builder pattern (`workspace-template/shell/menus.js`,
     tested by `hack/menus.test.mjs`).
3. **The zero state shows one unobtrusive entry point.** A tile in the zero
   state (P5) shows exactly one new thing: the `⇈` layout button (§3.1). There
   is no chip, no frame chip, no launcher banner, no target picker, no terminal
   notice and no request per frame, and existing `bx` commands print exactly
   what they print today.
4. **State is always visible and sticky.** Cloud Run's silent sticky pin is a
   documented surprise ([research/prior-art.md](research/prior-art.md), Google
   Cloud Run). Once a tile leaves the zero state, its live-reload state shows
   without a click in:
   - the title-bar chip, in both bar modes (§2);
   - the empty window's banner (§2.7);
   - the frame chip, for everyone with terminal access to the tile (§6.4);
   - `bx status` and `bx live-reload` (§8);
   - a grey line in every open terminal when it changes (§9).

   Nothing in the UI times out or reverts by itself.
5. **Resume semantics are explicit.** Netlify's unlock does not ship the
   backlog, while Cloud Run's `--to-latest` jumps to the newest
   ([research/prior-art.md](research/prior-art.md) §2(c)). xbin's resume ships
   the backlog at once (glossary: "switches to the work tree at once"). Every
   Resume, Attach and Reload now label, tooltip and confirmation therefore
   states what ships now (checkpoint and file count) and what later saves do.
6. **A code move onto the live reload target pauses live reload, and says
   so.** Every deploy, promote and roll back onto the live reload target
   carries "Live reload pauses" in its confirmation. Afterwards the panel's
   header offers **Resume live reload** as the undo (Vercel's "Undo Rollback",
   [research/prior-art.md](research/prior-art.md) §Vercel).
7. **The server decides; the UI renders.** Who may do what (`can` and `why`,
   §4.1) and what an operation will do (the state and the diff, §5.1) come
   from the server. The browser never re-derives [05-model.md](05-model.md)
   §10 and never guesses a consequence. D39 is the precedent: "UIs confirm
   with the report; bx prompts with it."
8. **Glossary words only, from one table.** Every string is in §12 and lives
   in one pure module (NP-10-3); `bx` prints the same words.

## 2. The terminal window title bar

Today, left to right (`web/frame-titlebar.js:26-49`):
- the path, then the tab strip, then `+`;
- on the full bar: the layout group `>_ { } ⇋ ▤ ⇄N` (L121-136), a spacer and
  `settings()`: the per-session pickers (network, tile API, `⧉ VM`, GPU;
  L145-178), ending in the tile-scoped `layerButtons` (`⬆ base update`, `⟲`;
  L205-213);
- on the degraded bar: `⋯` instead, which opens the tools row (L100-102);
- last, `✕`.

This design adds the live-reload chip and the Reload now offer (tile-wide), a
per-session target picker, and the `⇈` layout button (§3.1).

### 2.1 The live-reload chip

A `<button class="lr">` showing the tile's live-reload state. It renders only
when the tile is out of the zero state.

| State | Full bar | Degraded bar | Tooltip and `aria-label` |
|---|---|---|---|
| Zero state | — | — | — |
| Attached to the primary, other deployment state exists | `● Live reload: main` | `● main` | Live reload: main — every save reaches everyone using apps/crm. |
| Attached to a non-primary deployment | `● Live reload: dev` | `● dev` | Live reload: dev — saves reach apps/crm+dev. The primary, main, is pinned to c:3f2a1c9. |
| Paused, N files changed | `📌 Live reload paused · 3` | `📌 3` | Live reload paused by ana 12m ago — 3 files changed since c:3f2a1c9, which main runs. Reload now ships them to main once. |
| Paused, nothing changed | `📌 Live reload paused` | `📌` | Live reload paused by ana 12m ago — no changes since c:3f2a1c9. |
| Paused, the last deploy to the last target failed | `📌 Live reload paused · deploy failed` (red) | `📌 !` (red) | The last deploy to main failed; main keeps running c:3f2a1c9. Reload now retries. |

Rules:
- `N` is the file count of the server's diff stat from the last target's
  checkpoint to the work tree (`GET /api/xbin/deployments/diff?stat=1`,
  [11-contract.md](11-contract.md) §1.11), fetched while the window is open and
  refetched, debounced by one second, on each `deployments` event with op
  `worktree` (11-contract §3.3). The browser never diffs.
- "by ana 12m ago" comes from the last target's newest deploy-log entry with
  `how: "pause"` (`by`, `finishedAt`). When that entry says `agent: true`, it
  reads "by ana (agent)".
- "deploy failed" shows while the last target's `lastDeploy.result` is
  `failed`, and clears with its next `ok`.
- On the degraded bar, names longer than 10 characters are cut with `…`; the
  tooltip carries the full sentence.
- Clicking the chip opens a `<bx-menu>` anchored under it, a bottom sheet on
  phones, exactly like the `+` launcher (`web/bx-frame.js:655-658`). Its items,
  in order:

| Item | Shown when | Does |
|---|---|---|
| header `Live reload` | always | — |
| the tooltip sentence, as a disabled item | always | — |
| `⇡ Reload now · 3` | paused | §5.2 row 3 |
| `Pause live reload` | attached | §5.2 row 1 |
| `Resume live reload on main` (the last target) | paused | §5.2 row 2 |
| `Attach live reload to ▸`, a submenu of every other deployment | two or more deployments | §5.2 row 4 |
| separator, then `⇈ Deployments…` | always | `open('deployments')` |

- An item the viewer may not use stays in the menu, `disabled`, with the
  server's reason as its `hint` (§4.2).

### 2.2 The Reload now offer

On the full bar, directly after the chip:
`<button class="offer">⇡ Reload now · 3</button>`.
- It has an accent outline, the launcher's `.lresume` look
  (`web/frame-launcher.js:216-218`), and never the amber of `⬆ base update`,
  so the two offers can't be confused.
- It shows only when live reload is paused, `N > 0` and the state's
  `caller.can.reloadNow` is true. In every other case Reload now lives only in
  the chip menu, disabled with its reason where that applies.
- The degraded bar has no separate offer. The compact chip's count is the cue,
  and the first action in its menu is Reload now.

Reload now always means the glossary's tile-wide act: checkpoint the work tree
and deploy it once to the deployment live reload last followed. Every viewer's
frame of that deployment reloads once. There is no "reload only my frame"
action. (This closes the first open question of
[research/ui-surfaces.md](research/ui-surfaces.md).)

### 2.3 The target picker

The target deployment belongs to a session (glossary). The bar shows it as a
picker next to the network picker:
- `<select class="scope target">` with options `target: main`, `target: dev`,
  … (the glossary's "target: dev"). Like every data-built picker it marks its
  option with `live(.selected)` (`web/frame-titlebar.js:140-144`).
- It shows only when the tile has two or more deployments and the active tab
  has a live session: not for ended or history agent tabs, and not on the
  launcher.
- Its value is the target the server echoes in the session frame (a
  `deployment` field, handled like `net`, `web/bx-frame.js:739-743`): a name,
  or none for a session that follows the primary, shown as
  `target: main (primary)`. Clients must check the echo; a missing echo means
  an older xbind that can't target deployments, and the tab ends and says so
  (11-contract §7.4).
- Changing it restarts the session, as every picker does: the target is fixed
  for the session's life (NP-11-2). A shell goes through `_respawn`, whose
  confirm becomes "Restart this terminal targeting dev?"
  (`web/bx-frame.js:753-765`), and reconnects with `deployment=<name>`. An
  agent goes through `restartAgent`, which resumes its conversation
  (`web/frame-launcher.js:95-124`), with `?deployment=<name>` on the restart.
- **Stale-target offer.** When live reload moves to a deployment other than a
  live tab's target, that tab's picker takes the amber offer look (the
  `.upgrade` style, `web/frame-titlebar.js:259-264`), with the tooltip "Saves
  now reach dev, but this terminal calls main — switching restarts it". It
  clears when the tab switches or live reload moves back. It never switches by
  itself: a terminal deliberately pointed at the primary stays pointed there.

### 2.4 Placement within D107's degrade rules

D107 ([../DECISIONS.md](../DECISIONS.md)): the bar is measured after every
render and resize (`fitBar`, `web/frame-titlebar.js:76-96`). It degrades when
it overflows and comes back once the window is as wide as it needed; `barKey`
(L61-62) lists what the width depends on.

| Bar mode | Where the new controls render |
|---|---|
| Full | `settings()` renders, in order: target picker, network, tile API, `⧉ VM`, GPU, **chip**, **Reload now offer**, `⬆ base update`, `⟲`. The chip and the offer render in **both** branches of `settings()` (`web/frame-titlebar.js:106-109`), so ended and history agent tabs and the empty window keep them. `⇈` renders in `layoutGroup`. |
| Degraded (under 640 px, the phone sheet, or measured overflow) | The **compact chip** renders in the title-bar row itself, between `+` and `⋯`, so the state never hides behind `⋯`. The tools row (`toolsRow`, L100-102) renders `layoutGroup` (with `⇈`) and `settings()` **without** the chip and the offer. |

- `barKey` gains: the attached name (or `""`), whether live reload is paused,
  `N`, the deployment count, whether the offer shows, whether the last deploy
  failed, and each tab's target. A change resets `_barNeed`
  (`web/bx-frame.js:239-240`) and fitBar measures again, as D107 requires.
- The compact chip is `flex: none` with `max-width: 12ch`. The tab strip
  absorbs the width, as today.
- D107's degrade order is unchanged: the path and the network label shrink,
  then the bar degrades, then tabs shrink to 56 px and the strip scrolls.

### 2.5 dragWindow's target rules

`dragWindow` ignores a pointerdown only on `button, select, .tab`
(`web/bx-kit.js:145-146`); pressing anything else on the bar drags the window.
Therefore:
- the chip, the offer and `⇈` are `<button>`s, and the target picker is a
  `<select>`;
- the glyph and the count are `<span>`s inside their button
  (`closest('button')` catches them);
- no element on the bar may put a click handler on a `span` or a `div`.

### 2.6 Glyphs

The taken glyphs and words are listed in
[research/ui-surfaces.md](research/ui-surfaces.md) (hazards) and
[research/terminology-census.md](research/terminology-census.md) (its
"live reload" and "pause" entries).

| Glyph | Means | Where | Why this one |
|---|---|---|---|
| `●` | runs the work tree (live reload attached) | chip, panel code column | bx-code already labels uncommitted work "● Working tree" (`web/bx-code.js:355`), the same object |
| `📌` | pinned to a checkpoint | chip, panel, frame chip, sidebar | "pinned" is the glossary term; the glyph is unused in the repo; it is not ⏸, which is Disable (`workspace-template/shell/menus.js:114`) |
| `⇡` | Reload now | offer, chip menu | same Arrows block as the `⇄` and `⇋` already on the bar; not ⟲, which resets the terminal layer (`web/frame-titlebar.js:211-212`), nor ⟳, which refetches the tile admin (`workspace-template/shell/bx-tile-admin.js:518`) |
| `⇈` | the Deployments layout | layout group, tile-menu line | unused; vertical, so it reads apart from the horizontal `⇄` beside it |
| `🛡` | protected primary | panel, `bx` | unused; 🔒 already means the namespace sandbox and read-only screens (`workspace-template/tiles/admin/tabs/runtime.js:419`) |
| `↗` | open in a new tab | panel | the apidocs tile's "spec ↗" precedent |

This feature never uses ⏸, ⟲, ⟳, 🔒, ▶ (Enable, `workspace-template/shell/menus.js:112`)
or ⧉ (VM, unpin). Every glyph is `aria-hidden="true"`, and its control's
`aria-label` carries the words.

### 2.7 The launcher

The empty window (`web/frame-launcher.js:152-184`) shows, above the session
cards, one line for the tile-wide state, modelled on the `.lbase` banner
(L160-164):
- paused: an amber banner, "Live reload is paused: 3 files changed since
  c:3f2a1c9, the checkpoint main runs.", with the `⇡ Reload now` button when
  the viewer may use it;
- attached to a non-primary deployment: a plain line, "Live reload: dev —
  saves reach apps/crm+dev; main is pinned to c:3f2a1c9.";
- the zero state, or attached to the primary: nothing.

When the tile has two or more deployments, each session card's subtitle gains
"· target: dev", naming the target a new session gets.

## 3. The Deployments layout

### 3.1 The ⇈ layout button

- `layoutGroup` (`web/frame-titlebar.js:121-136`) gains a sixth button, `⇈`,
  on every tile, titled "deployments — live reload, deploy, promote, roll
  back". With two or more deployments it carries their count, `⇈ 2`, the way
  `⇄` carries the proposal count (L132-134); the count is in `barKey`. `.on`
  marks it active.
- It opens layout `'deployments'`:
  - `_layout`'s documented union (`web/bx-frame.js:95`) and `open(layout)`'s
    comment (L533-541) gain it, so the shell's tile menu can open it (§7);
  - `_setLayout` widens the window to 960 px for it, as for code, split and
    prs (L792-800);
  - `.panels` mounts `<bx-deployments>` lazily, like bx-logs and bx-prs
    (L843-844);
  - the per-user window pref records `'term'` in its place (NP-10-2), so a
    downgraded xbind never restores a layout it can't draw (`_restoreTerm`
    accepts any string, L328).
- **Test impact:** `hack/ui-harness/passes/agenttab.js:238-239` asserts
  exactly five `.lyt` buttons. It becomes six in the same change.

### 3.2 Structure

`<bx-deployments component="apps/crm">` is a new shell-only `/vendor/`
element. [13-surfaces.md](13-surfaces.md) names the file (proposal:
`web/bx-deployments.js`), and [/docs/frontend-kit.md](/docs/frontend-kit.md)
lists it under Shell-only modules. It follows bx-prs's shape, a side list and
a main pane (`web/bx-prs.js:41-95`). It receives its host frame as a property
and asks every question through the frame's `_ask`/`_confirm`
(`web/bx-frame.js:714-725`). There is then one dialog at a time, and the
harness drives it with the existing `dialog`/`answerDialog` (§14).

```
┌ header ──────────────────────────────────────────────────────────────┐
│ 📌 Live reload paused · 3 files changed since c:3f2a1c9 (main)         │
│ (⇡ Reload now)  (Resume live reload on main)                          │
├ side, 230px ─────────────┬ main pane ─────────────────────────────────┤
│ tile-wide                │ overview · deploy log · logs ·             │
│ main  primary 🛡          │ registrations · view                        │
│   📌 c:3f2a1c9 · healthy  │                                            │
│ dev                      │ (the selected row)                          │
│   📌 c:7b19e02 · idle     │                                            │
│ + Add deployment…        │ actions row, sticky at the bottom           │
└──────────────────────────┴─────────────────────────────────────────────┘
```

- The **header** always shows the live-reload sentence (§12.1) and the
  live-reload buttons that fit the state: Pause live reload, Resume live
  reload, Reload now, Attach live reload ▸.
- The **side list** starts with "tile-wide" (the primary, protection, outbound
  edges, caps), then one row per deployment (the primary first, then by name),
  then "+ Add deployment…".
- The **main pane** shows the selected row. The default selection is the live
  reload target, else the primary.
- The panel refetches on each `deployments` event for its tile (ops `record`,
  `deploy`, `worktree`, `data`, `status`, `notify`; 11-contract §3.3),
  debounced 250 ms like bx-code (`web/bx-code.js:267-272`).
- **bx-code needs the same signal.** It refreshes its work-tree diff only on
  `reload` and `build-ok` (`web/bx-code.js:267-272`), and a save while live
  reload is paused publishes neither, only op `worktree` (11-contract §3.5).
  bx-code must also refresh on its tile's `deployments` op `worktree`, or the
  Code panel goes stale exactly while live reload is paused.

### 3.5 Promote, with the diff first

A promotion onto the primary is the operation people fear most, so the panel
shows exactly what the receiving deployment gets before it asks.

1. "Promote dev → main…" in dev's overview opens the promotion view in the
   main pane, with `From` and `To` selects (defaults: this deployment and the
   primary) and the diff between what B runs and what B would receive, from
   `GET /api/xbin/deployments/diff` (11-contract §1.11):
   - A is pinned: A's checkpoint against B's checkpoint (between checkpoints);
   - A follows the work tree: `to=worktree`, which captures a checkpoint of the
     work tree when the view opens (against the work tree).
2. The diff renders through bx-code's exported `diffHTML` and `diffStats`
   (`web/bx-code.js:44`, `:70`), as bx-prs does (`web/bx-prs.js:15`), under a
   stats line: "c:3f2a1c9 → c:7b19e02 · 3 files, +40 −12". The two ids are the
   answer's `X-XBin-Checkpoint-From` and `X-XBin-Checkpoint-To`.
3. **What you saw is what ships.** Confirming sends the reviewed
   `X-XBin-Checkpoint-To` as `expect` (NP-11-4). If the work tree changes while
   the view is open (op `worktree`), the view says "The work tree changed
   since this diff was taken." with a **Refresh** button. A promotion sent with
   the old `expect` answers 409, and the view refreshes the diff and says "The
   code changed since you reviewed it — review the new diff."
4. "Promote dev → main…" opens the confirmation (§5.2 row 7), whose message
   repeats the stats.
5. An empty diff reads "main already runs this code" and disables the button.

Deploy to X uses the same view when X is the primary. For a non-primary X it
goes straight to the confirmation, whose message carries the stats. Bar
actions (Reload now, Resume) have no room for a diff: their confirmation
carries the stats and says "The Deployments panel shows the diff."

### 3.6 Roll back from the deploy log

The deploy log tab lists X's entries, newest first
(`GET /api/xbin/deployments/log`, 11-contract §1.10; failed attempts
included):

| Column | Example |
|---|---|
| code | `📌 c:1e9d0aa`, or `● work tree` for entries that follow it (resume, attach) |
| how | the entry's `how`, in words: deploy · promote (from dev) · roll back · reload now · resume live reload · live reload paused · live reload attached · added · protected |
| result | ok · failed (with its `error`) · superseded · cancelled; in flight: queued · building · starting |

> **Live reload: main** — every save reaches everyone using apps/crm.
>

> Reload now ships your changes when you're ready.
>

- `runtime: "cgi"`: both (05-model.md §12);
- chrome tiles and tiles holding `xbin` capabilities: Add only; they may pause
  live reload (P19);
- the per-tile or per-workspace cap: Add only.

## 4. Permissions in the UI

### 4.1 The state endpoint carries the viewer

Today the frame knows nothing about the viewer's level. A 403 from
`/ws/term/env` silently becomes `{}` (`web/frame-launcher.js:34`), because that
endpoint is terminal-gated (`termEnvGate`, `internal/server/server.go:335-351`).
The deployments state therefore comes from its own endpoint,
`GET /api/xbin/deployments?tile=<tile>` ([11-contract.md](11-contract.md)
§1.3), whose answer carries what the UI needs to render permissions:
- `caller`: the viewer's `level` (read, write, terminal, admin, or tile),
  `manager`, `readOnly` (view-as) and tile-level `can` with a `why` for each
  false (pause, resume, reload now, add, edges, protect);
- per deployment, `can` and `why` for every operation on it (open, deploy,
  promote to, roll back, attach, remove, reset, seed, vault copy, deliveries,
  alwaysOn, Run now, primary);
- `allowed`: what the tile itself may do (pause, have deployments), with the
  reason (isolation, cgi, chrome), and `limits` (the caps).

Readers get 403 from that endpoint (NP-11-19). The frame treats the 403 as
"read level", never as a silent `{}`, and shows the `/api/xbin/components`
summary (`deployments: {primary, liveReload, count}`, 11-contract §8) with the
line "Details need write access to apps/crm."

Refusal texts name tile managers by role ("the tile's owner, its org's
admins, or a workspace admin", 11-contract §1.14). Naming the people, as D33's
who-can-approve hints do, would need the state to carry them (NP-10-9).

`loadTileState` (`web/frame-launcher.js:35-40`) fetches the state when the
window opens and on every relist, and the frame refetches it on each
`deployments` event for its tile. The frame chip (§6.4) starts from the
components summary instead, so a zero-state tile costs no request.

### 4.2 Rendering rules

- A control that doesn't apply to the current state is **hidden** (Resume
  while attached; Seed on the primary).
- A control that applies but that the viewer may not use is **disabled**,
  never hidden. Its `why` becomes its `title`. Touch has no tooltips, so the
  reason also shows as a muted line under the panel's actions row, and as the
  `hint` of a bx-menu item. The VM toggle is the tooltip precedent
  (`web/frame-titlebar.js:194-199`).
- The UI never sends a request whose `can` is false.
- `can` is read again after every operation and every `deployments` event. A
  stale `can` is corrected by the server's refusal (§4.5).

### 4.3 What each level sees enabled

| Viewer | Sees | May |
|---|---|---|
| read | the components summary only: the header sentence and "Details need write access"; no frame chip | nothing; `open ↗` for the primary only |
| write, including `noTerminal` accounts (D88) | the full state and the deploy log | open non-primary deployments (`open ↗`, the view tab) |
| terminal, and the tile's terminal and agent tokens | plus logs, the frame chip, the target picker | pause and resume live reload, reload now, attach live reload; add, remove, deploy, promote, roll back, reset, Run now; deploy to the primary unless it is protected (parity, P4) |
| tile manager, in their own session | everything | plus seed, vault copy, deliveries, alwaysOn, edge policy, reassign, protect; code moves onto a protected primary |
| view-as (D64) | what the viewed user sees | nothing (§4.4) |

### 4.4 View-as

A view-as session is read-only. The middleware refuses every non-GET with
"read-only: you are viewing the workspace as another user — exit the view (top
banner) to make changes" (`internal/server/impersonate.go:19`, `:33-39`). The
UI:
- computes nothing itself: GETs answer as for the viewed user (11-contract
  §0.5), so `caller.readOnly` is true and every `can` is the viewed user's;
- renders every action disabled. Where `can` says yes the tooltip reads "dev1
  may do this — you are viewing as dev1 (read-only)"; elsewhere it gives the
  ordinary reason. An admin sees exactly what dev1 could do, and no request is
  sent.

### 4.5 Refusals that still happen

A race, such as someone protecting the primary a second ago, can still produce
a refusal. Every request carries the state's `seq` (and code moves carry
`expect`), so a moved record or moved code answers 409 instead of acting on
stale facts (11-contract §1.2). Then:
- a 409 for a stale `seq` refetches the state and re-opens the confirmation
  with the new facts; a 409 for `expect` refreshes the diff (§3.5);
- any other refusal shows its `error` text (11-contract §1.14) verbatim,
  inside the section that asked, like the tile admin's `_do`
  (`workspace-template/shell/bx-tile-admin.js:163-174`), or, for a bar action,
  as `_confirm('Reload now was refused', error, 'OK')`, like restartAgent's
  failure (`web/frame-launcher.js:121`), and refetches the state;
- a refusal is never a silent no-op, and never only a toast.

## 5. Confirmations

### 5.1 Rules

- Every confirmation is a data-only `bx-dialog` spec passed through the
  frame's `_ask`/`_confirm` (`web/bx-dialog.js:9-20`). Its strings render as
  text only, D56's anti-phishing property. A dialog holds no markup, no links
  and no diff; the diff lives in the panel (§3.5).
- The message has up to four labelled lines, in this order, each present only
  when it says something (the dialog keeps line breaks, `web/bx-dialog.js:49`):
  - **Code:** what code goes where: checkpoints and file stats.
  - **Data:** what data moves. Almost always "nothing moves".
  - **Pauses:** live reload pausing, or a deployment stopping.
  - **Affects:** who notices: everyone using the tile, only the people using
    apps/crm+dev, or nobody now.
- The facts come from the server: the state (whether live reload pauses
  follows from its `liveReload`, `primary` and `protectedPrimary`), and for
  code moves the diff stat and its checkpoint ids (11-contract §1.11). The
  request then carries the state's `seq` and the diff's `expect`, so the
  confirmation is exact: if either moved, the answer is 409 and nothing
  happens (§4.5). This is D39's rule, "UIs confirm with the report", with the
  state and the diff as the report.
- The title is a question naming the effect. The OK button is the verb, never
  "OK" or "Yes". Cancel comes first.
- The OK button carries `danger: true` for removing a deployment, resetting
  data, a seed that replaces data, and reassigning the primary.
- A **required acknowledgement** is a checkbox field, and ticking it is what
  sends the route's `confirm` token (NP-11-5): removing a deployment
  (`erase`), resetting data (`erase-data`), seeding, including an add that
  seeds (`copy-data`), and reassigning the primary (`data-stays`). If the
  dialog resolves with the box unticked, the host re-opens it with `error`
  set: "Tick the box to confirm."
- Escape, the backdrop and Cancel resolve `null`, and nothing happens.

## 6. Viewing non-primary frontends

### 6.1 In the panel: the view tab

The main pane's **view** tab embeds the selected non-primary deployment's
frontend as `<bx-frame src="apps/crm+dev" no-edit>`, the qualified `src` of
11-contract §2.5:
- Its iframe loads `/c/apps/crm+dev/`, and frame-info mints its bootstrap
  token with `?component=apps/crm&deployment=dev` (11-contract §7.2). No new
  attribute is needed; bx-frame's attributes stay the compatibility surface
  [/docs/frontend-kit.md](/docs/frontend-kit.md) promises.
- Non-primary events carry `component: "apps/crm+dev"` (11-contract §3.2), so
  reload targeting and build overlays work unchanged: the view frame reacts
  only to its deployment's events, and the host's primary frame only to the
  primary's (`isReloadTarget` compares `src`, `web/events-socket.js:40-49`).
- It always wears its name as a label, `dev`, so it can't be mistaken for the
  primary (n8n's colour label that tells people where they are,
  [research/prior-art.md](research/prior-art.md) §n8n).
- It never opens a terminal window of its own.

### 6.2 Full page, in a new tab

`open ↗` opens `/c/<tile>+<name>/` in a new tab with
`window.open(url, '_blank')`, like the shell's `openFullPage`
(`workspace-template/shell/bx-shell.js:906`). The address bar shows the
deployment. v1 draws nothing into the tile's own document (the repo's one
sanctioned HTML transform, CLAUDE.md); a tile that wants to label itself reads
`xbin.deployment` (11-contract §6). Open question 1 asks whether the injected
client should draw a corner label.

### 6.3 Why not as shell cards in v1

- Layouts key tiles by path: `_isOpen`
  (`workspace-template/shell/bx-shell.js:996`) and the canvas `repeat`, keyed
  by `o.path` (`workspace-template/shell/bx-canvas.js:419`, `:424`). A second
  card for `apps/crm` would break old shells, so a card would have to be
  stored as `apps/crm+dev`.
- That entry has no `/api/xbin/components` row: an old shell would draw it
  with no runtime dot, no tile menu and no sidebar row. The iOS app reads
  layout paths (`native/ios/Packages/XbinCore/Sources/XbinCore/Client/Catalog.swift:187`)
  and resolves tiles by `/` boundaries (`.../Client/TileLoading.swift:74-79`),
  so it would find no tile for it. After an xbind downgrade the entry points
  at nothing.
- Org screens are shared (D55), so one user's `+dev` card would reach every
  member's shell, old or new, and an app that lags months behind.

v1 therefore has no deployment cards: the view tab and the full-page tab cover
viewing. A later rung can add cards once shells and the app understand
qualified layout entries.

### 6.4 The frame chip

bx-frame's `.frame-wrap` (`web/bx-frame.js:818-829`) is the only
binary-served surface drawn over a tile, so it carries the one ambient
indicator that reaches old shells.
- **For whom:** viewers with terminal level on the tile, the people whose
  saves are affected. Read and write viewers see a normal app and no chip.
- **When:** the frame's deployment is pinned while live reload is paused or
  attached elsewhere. Never in the zero state, and never while live reload is
  attached to the frame's own deployment.
- **What:** a 16 px `<button class="dchip">` holding `📌`, at the top right,
  left of the edit button's spot, at 55 % opacity: the edit button's quiet
  manners (`web/bx-frame.js:126-132`). Hover or focus expands it to "main
  pinned to c:3f2a1c9 · live reload paused", or "main pinned to c:3f2a1c9 ·
  saves reach dev". It carries no file count, which would cost a confined diff
  per tile per page. A click opens this tile's terminal window on the
  Deployments layout.
- The view-tab frame (§6.1) shows its deployment's name instead, always.
- **Data, in two steps:**
  - the `deployments` summary on the tile's existing `/api/xbin/components`
    row (`{primary, liveReload, count}`, 11-contract §8; the `native`,
    `origin` and `sandbox` precedents, `internal/server/api.go:130-160`). It
    is absent for zero-state tiles, so their rows stay byte-identical and cost
    nothing. The frame reads it through frame-info's per-page cache
    (`web/frame-info.js:44-51`), updated from `deployments` events and
    refetched when the page becomes visible;
  - only for a tile whose summary shows a pinned primary, one
    `GET /api/xbin/deployments` per page: a 403, or a `caller.level` below
    terminal, means no chip; otherwise it gives the checkpoint for the text.
- The chip sits inside `.frame-wrap`, so hovering it counts as hovering the
  tile; the reload-focus rules (`web/bx-frame.js:419-461`) are unaffected.

## 8. bx CLI

[11-contract.md](11-contract.md) §9 owns the commands, flags, output format,
waiting and exit codes. It refines the glossary's proposals without changing a
noun: `bx live-reload pause|resume|now|attach`, `bx deployment
ls|add|rm|primary|protect|seed|reset|vault-copy|deliveries|always-on|edge|run-now|log|diff`,
`bx deploy`, `bx promote` and `bx rollback`, dispatched through `moreCmds`
(`cmd/bx/native.go:28-32`) because `cmd/bx/main.go` is at its 1150-line
budget. This section fixes the human side on top of that contract.

### 8.1 What bx prints before it acts

Every command that moves code or data prints a summary before it asks or
acts. The summary uses §5.1's four labelled lines and the same facts the panel
uses: the state, and for a code move the diff stat whose
`X-XBin-Checkpoint-To` bx then sends as `expect` (11-contract §9.2). A code
move onto the primary always names its audience.

```
$ bx promote apps/crm dev main
Promote dev → main (the primary of apps/crm)
  Code     main runs c:7b19e02 (the work tree now) · 3 files, +40 −12 against c:3f2a1c9
  Data     only code moves — main keeps its data, secrets, cron jobs and routing
  Affects  everyone using apps/crm: frames reload once; WebSockets and SSE drop at the 30 s drain
Promote dev → main? [y/N] y
apps/crm: promote 44 dev → main c:7b19e02 … building … ok (38s)
```

- The words are §12's: "pinned c:3f2a1c9", "work tree", "started empty".
- Glyphs appear only in human output. `--json` prints the route's answer
  verbatim and nothing else on stdout (11-contract §9.1).

### 8.2 Prompts and `--yes`

- On a terminal, bx asks `<question> [y/N]`, as `bx owner --transfer` does
  (`cmd/bx/org.go:430-436`).
- Without a terminal and without `--yes`, it prints the summary, names
  `--yes` and exits 2 (11-contract §9.1). bx already checks `term.IsTerminal`
  (`cmd/bx/passphrase.go:16`).
- `--yes` is required for the data-bearing commands and for `deploy`,
  `promote` and `rollback` onto the primary (NP-11-5). This document extends
  the list to `live-reload now`, `live-reload resume` and `live-reload attach`
  whenever they move code onto the primary, because they ship to everyone
  exactly as a deploy does (NP-10-6). An agent then can't ship to the primary
  without saying `--yes`, its statement that the user asked (§10).
- `--yes` skips the prompt, never the summary.

### 8.3 XBIN_DEPLOYMENT and targets

- Read commands (`bx status`, `bx logs`, `bx deployment log`) default to
  `$XBIN_DEPLOYMENT` when the tile is `$XBIN_COMPONENT` (DR3, 11-contract
  §0.4), and every such output names the deployment ("apps/crm+dev").
  Self-scoped writes (`bx vault set`, cron jobs, subscriptions) act on the
  session's bound deployment by the server's rule (DR1).
- A command that moves code never takes its target from the env: `bx deploy`
  needs `--to`, `bx promote` both names, `bx rollback` the deployment.
  `bx live-reload resume` defaults to the last target, which its summary
  names.
- `bx deployment ls` marks the row the session targets with "← this
  terminal".
- Only backend calls to `/api/<tile>/…` are confined to the session's target
  (P12). xbind's own reads, such as logs and status, take any deployment of
  the tile.

### 8.4 Refusals and exit codes

- A refusal prints the server's `error` text (11-contract §1.14) verbatim. On
  a protected-primary 403, bx adds "deploy from the terminal window's
  deployments panel as a tile manager, or with bx on the host" instead of
  today's scoped-terminal hint (`cmd/bx/main.go:264-270`; 11-contract §9.1).
- Exit codes are NP-11-17's: 0 done, 1 a refused or failed request, 2 usage or
  `--yes` needed, 3 this xbind has no tile deployments, 4 the deploy ran and
  failed (the deployment keeps its previous code), 5 still running when bx
  stopped waiting. Today bx exits 1 on every error (`cmd/bx/main.go:105-108`)
  and 2 on usage (L175).
- An agent needs to tell "not yours to do" from "failed". A refusal by
  authority or policy (a 403, or a 409 saying the tile can't, such as
  isolation or cgi) should exit 6 instead of 1 (NP-10-7). Until that is
  decided, the agent guidance keys on the message, not the code (§10.2).

### 8.5 Existing commands

- `bx status` prints a `deployments:` line when the tile has a record
  (11-contract §9.3), in §12.1's words: `live reload paused · 3 files changed
  since c:3f2a1c9`, or `live reload: dev · main pinned to c:3f2a1c9`, plus the
  session's target. A zero-state tile's output is unchanged.
- `bx logs` streams a named deployment's log through
  `GET /logs?deployment=` (11-contract §9.3), not the direct file read, which
  already fails in isolated terminals
  ([research/side-findings.md](research/side-findings.md) #22).
- `bx ls` is unchanged. It lists tiles, never deployments.

## 9. Terminal notices

A grey line appears in the open terminals of a tile when its tile-wide state
changes, so someone typing in a terminal learns that their saves stopped, or
started, reaching somebody. The framing is exactly netNote's,
`\r\n\x1b[90m[…]\x1b[0m\r\n` (`web/bx-terminal.js:634-637`).

Mechanism (NP-10-1): the frame's deploy module handles the `deployments`
events for its tile, op `deploy` when a result is final and op `record` when
`liveReload`, `primary` or `protectedPrimary` changed (11-contract §3.3), and
calls a new public `note(text)` on each of its `<bx-terminal>` elements
(bx-terminal is at 713 of 900 lines). `note()`:
- writes at once while the terminal shows its normal buffer;
- while a full-screen program holds the alternate buffer (vim, less, a TUI),
  keeps only the latest note and writes it when the program exits, so no
  screen is ever corrupted;
- skips the tab whose own session performed the act, where bx has already
  printed the result. That needs the event to name the acting session, which
  11-contract's events don't yet do (NP-10-1).

Agent tabs get no transcript lines: agents learn the state from bx (§10). The
iOS app's terminal gets none either.

| Event | Line |
|---|---|
| paused | `[live reload paused by ana — main is pinned to c:3f2a1c9; saves no longer reach it]` |
| resumed | `[live reload resumed on main by ana — saves reach main again]` |
| attached elsewhere | `[live reload attached to dev by ana — saves reach apps/crm+dev; main is pinned to c:3f2a1c9]`, plus ` — this terminal still calls main` when the tab's target differs |
| code moved (deploy, promote, roll back, reload now) | `[main now runs c:7b19e02 — promoted from dev by ana]` |
| a code move failed | `[deploy to main failed — main keeps running c:3f2a1c9; the Deployments panel has the output]` |
| primary reassigned | `[dev is now the primary of apps/crm (by ana) — it serves dev's data]` |
| protection changed | `[main is protected by ana — only tile managers change its code]` |
| the tab's target removed | `[deployment dev was removed by ana — this terminal's API calls fail until you switch its target]` |

Op `worktree` (saves while live reload is paused) never writes a line. A line
can land between a prompt and a half-typed command, exactly as the existing
`[reconnecting…]` line does (`web/bx-terminal.js:676`); the command stays in
the shell's buffer and only its display is split.

### 14.4 Restoring state after passes

Live-reload state belongs to the tile and outlives a pass, so a failed pass
could leave later passes (reloadFocus, agentTab) running against a changed
tile. Every deployment pass must:
- change state only on `apps/deploy-demo` (`apps/crawler` is used only for
  refusals, which change nothing);
- call `resetDeploys(ctx, tile)` **at its start and in `finally`**. Through the
  API it reassigns the primary to main, unprotects it, sets every edge back to
  `default`, removes every other deployment and resumes live reload on main,
  sending the `confirm` tokens those routes need. It then asserts that the
  state answers `record: false`: P5's "opting out returns to it" doubles as
  the check;
- restore `index.html`'s original bytes;
- end its sessions and delete the `term:<tile>` pref, as today's passes do.

## Divergences from the model

1. **P21's "cannot target" collides with the glossary's "target
   deployment".** 05-model.md §10 says that while the primary is protected
   "terminal/agent tokens cannot target the primary at all", and P21 says
   "terminal/agent tokens cannot target it". Read with the glossary's meaning
   of target, a terminal on a tile whose only deployment is a protected
   primary would have no valid target, and every such terminal would lose the
   primary's API. Recommended fix: reword both to "cannot deploy, promote,
   roll back, reload now or resume onto it", and state that a session may
   still target a protected primary (calls and reads work as today).
   11-contract DIV-6 reaches the same reading and builds it (§7.4); this
   document assumes it (§3.4, §5.2 row 11a).
2. **The target's lifetime is unspecified.** The glossary says the target
   "defaults to the live reload target, or the primary when live reload is
   paused", and §10 lists "set its target in a terminal". Neither says
   whether a running session follows later moves, and a running process's
   `XBIN_DEPLOYMENT` can't change. In flow B step 3, Ana's terminals opened
   before `dev` existed would keep calling main while her saves reach dev.
   Recommended fix: NP-11-2 (the target is fixed for the session's life and
   changed by a restart), plus this document's stale-target offer and notice
   (§2.3, §9).
3. **The glossary's "Data: empty" becomes false** as soon as a deployment
   writes anything (glossary §Spellings, "Data: empty / seeded from main").
   Recommended fix: "started empty" and "seeded from main · <when>"
   (NP-10-4).
4. **The deploy log's "how" list is incomplete.** The glossary lists "deploy /
   promote / roll back / reload now / resume", but 05-model.md §5's "Pause
   live reload" row deploys a checkpoint to the former target, and "Attach
   live reload to Y" pins it. Recommended fix: 11-contract's `DeployEntry.how`,
   which adds pause, attach, add and protect (§1.1); §3.6 shows them.
5. **Run now has no authority row.** 05-model.md §5 defines it, but §10 never
   says who may run it. Recommended fix: NP-11-10 (terminal level).
6. **"With the error shown" doesn't say where.** 05-model.md §5's "Pause live
   reload" row says that when the pausing build fails, X keeps serving "with
   the error shown until a reload now succeeds". 11-contract §3.5 publishes
   `build-*` for X's component on every deploy, so a failed deploy onto a
   pinned primary paints today's red overlay over a primary that is still
   serving its old code, for every viewer, until someone redeploys: saves no
   longer clear it. Recommended fix: NP-10-5.

## New proposals

- **NP-10-1 — Terminal notices are written by the browser.** bx-terminal gains
  a public `note(text)`, called by the frame's deploy module on the
  `deployments` ops `deploy` (final results) and `record` (when `liveReload`,
  `primary` or `protectedPrimary` changed). It defers while the alternate
  buffer is active. Those two ops gain the acting session's id when a session
  acted, so the acting tab is skipped. No `/ws/term` change is needed, and
  `internal/term/term.go` is at its 950-line budget.
- **NP-10-2 — The `'deployments'` layout isn't persisted.** The per-user
  window pref records `'term'` in its place, so a downgraded xbind never
  restores an unknown layout into an empty window.
- **NP-10-3 — One pure module holds every string.** All §12 strings and the
  state-to-controls logic live in one pure `/vendor/` module (proposal
  `web/deploy-state.js`), pinned by a node test. bx's strings follow the same
  table.
- **NP-10-4 — Data labels.** 11-contract's `data.state` values read:
  `main` as "original"; `empty` as "started empty", or "started empty · reset
  <when>" after a reset; `seeded` as "seeded from main · <when>".
- **NP-10-5 — A failed deploy onto a pinned primary doesn't paint the frame
  overlay.** It is reported through `deployments` op `deploy`, the chip, the
  panel, the terminal notice and bx's exit code. `build-error` and `build-ok`
  for the bare component stay tied to live-reload builds, as today. For a
  non-primary X, `build-*` for `<tile>+<X>` reaches only the view-tab frame
  and stays. This amends 11-contract §3.5's "`build-*` for X's component".
- **NP-10-6 — `--yes` also guards live-reload moves onto the primary.** Without
  a terminal, `bx live-reload now`, `resume` and `attach` need `--yes` when
  they move code onto the primary, extending NP-11-5's list: they ship to
  everyone exactly as a deploy does.
- **NP-10-7 — bx exit code 6 for refusals.** Refusals by authority or policy
  (a 403, and the 409s saying the tile can't: isolation, cgi, chrome, a cap)
  exit 6, next to NP-11-17's 3, 4 and 5, so an agent can tell "not yours to
  do" from "failed".
- **NP-10-8 — The ▤ logs layout follows the active tab's target.** bx-logs
  gains an optional `deployment` attribute (`observedAttributes`,
  `web/bx-logs.js:61`), sent as `/logs?deployment=`. The Deployments panel's
  logs tab uses the same element for the selected row.
- **NP-10-9 — The deployments state names the tile's managers.** Listing the
  user-owner and the owning org lets tooltips and refusals say who to ask, as
  D33's who-can-approve hints do; 11-contract §1.14's texts name only roles.
