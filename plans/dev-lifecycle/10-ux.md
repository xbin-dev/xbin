# 10 — UX: terminal window, shell, bx, agents

> Status: live — every surface, control, confirmation and string through which people and agents see and operate live reload, tile deployments and promotion (part of [plans/dev-lifecycle](README.md))

This document turns the model ([05-model.md](05-model.md)) into surfaces. It
owns placement, states, controls, confirmation text, the wording table, the
agent guidance text and the harness assertions. It does not own:
- the wire ([11-contract.md](11-contract.md)): endpoint names, fields and event
  shapes named below are 11-contract's, and where this document needs a field
  11-contract doesn't carry yet, it says so (NP-10-10);
- `bx`'s commands, flags, output format, prompts and exit codes: 11-contract
  §9 is authoritative, and §8 below adopts it verbatim;
- runtime behaviour ([07-runtime.md](07-runtime.md)), data
  ([08-data.md](08-data.md)) or the fabric ([09-fabric.md](09-fabric.md)).

Vocabulary is [01-glossary.md](01-glossary.md), verbatim. Facts about today
come from [research/ui-surfaces.md](research/ui-surfaces.md) unless another
research file is named, and every `file:line` was re-checked in this worktree.
File names follow [14-implementation.md](14-implementation.md) §0.3:
`web/deploy-state.js` (pure logic and strings), `web/frame-deploy.js` (the
frame's glue), `web/frame-testapi.js` (the frame's test names), and
`web/bx-deploy.js`, which defines `<bx-deployments>`.

Examples use tile `apps/crm`, deployments `main` (the primary) and `dev`,
checkpoints `c:3f2a1c9` (what main runs), `c:7b19e02` (a fresh checkpoint of
the work tree) and `c:1e9d0aa` (an older one), and the user `ana`.

## 1. Principles

1. **The terminal window first.**
   - `web/` is embedded in the binary (`assets.go:11`) and served under
     `/vendor/` with `Cache-Control: no-cache`, because "vendor changes on
     upgrade" (`internal/server/static.go:601`). bx-frame, frame-titlebar,
     frame-launcher, bx-logs, bx-dialog and bx-menu therefore reach every
     workspace at its next xbind upgrade.
   - The scaffold (shell, menus, tile admin, the admin tile) is copied once by
     `xbind init` and changes only through `bx builtin update`
     ([/docs/compat.md](/docs/compat.md) rules 2 and 4). bx-terminal's own
     comment names the trap (`web/bx-terminal.js:261-266`).
   - So every state in §12.1 must be visible, and every operation in §5 must be
     reachable, from the terminal window alone. A workspace that never runs
     `bx builtin update` has the whole feature.
   - New UI goes into new `/vendor/` siblings: `web/bx-frame.js` is at 866 of
     its 900-line cap, and frame-titlebar and frame-launcher were extracted for
     exactly that reason (`web/frame-titlebar.js:2-4`).
2. **Scaffold surfaces are garnish.** A card badge, sidebar badge, tile-menu
   line or admin row (§7):
   - must render nothing when the field it reads is absent (an older xbind);
   - must never be the only path to anything;
   - follows the shell's pure-builder pattern (`workspace-template/shell/menus.js`,
     tested by `hack/menus.test.mjs`).
3. **The zero state shows one unobtrusive entry point.** A tile in the zero
   state (P5) shows exactly one new thing: the `⇈` layout button (§3.1). There
   is no chip, no frame chip, no launcher banner and no terminal notice; the
   tile API select keeps exactly today's two options (§2.3); no request is
   made per frame; and existing `bx` commands print exactly what they print
   today.
4. **State is always visible and sticky.** Cloud Run's silent sticky pin is a
   documented surprise ([research/prior-art.md](research/prior-art.md), Google
   Cloud Run). Once a tile leaves the zero state, its live-reload state shows
   without a click in:
   - the title-bar chip, in both bar modes (§2);
   - the empty window's banner (§2.7);
   - the frame chip, for everyone with terminal level on the tile (§6.4);
   - `bx status` and `bx live-reload` (§8);
   - a grey line in every open terminal when it changes (§9).

   Nothing in the UI times out or reverts by itself.
5. **Resume semantics are explicit.** Netlify's unlock does not ship the
   backlog, while Cloud Run's `--to-latest` jumps to the newest
   ([research/prior-art.md](research/prior-art.md), cross-cutting synthesis:
   "decide, and show, what resume does"). xbin's resume ships the backlog at
   once (glossary: "switches to the work tree at once"). Every Resume, Attach
   and Reload now label, tooltip and confirmation therefore states what ships
   now (checkpoint and file count) and what later saves do.
6. **A code move onto the live reload target pauses live reload, and says
   so.** Every deploy, promote and roll back onto the live reload target
   carries "Live reload pauses" in its confirmation. Afterwards the panel's
   header offers two separate actions (§3.6):
   - **Undo**: roll the deployment back to the checkpoint the move replaced;
   - **Resume live reload**, with its own consequence text. After a roll back
     the work tree still holds the code that was rolled back from, so resuming
     ships it again, and the header and the confirmation say so.
7. **The server decides; the UI renders.** Who may do what (`can` and `why`,
   §4.1) and what an operation will do (a dry run's `impact`, §5.1) come from
   the server. The browser never re-derives [05-model.md](05-model.md) §10 and
   never guesses a consequence. D39 is the precedent: "UIs confirm with the
   report; bx prompts with it."
8. **Glossary words only, from one table.** Every string is in §12 and lives
   in one pure module, `web/deploy-state.js` (NP-10-3); `bx` prints the same
   words.

## 2. The terminal window title bar

Today, left to right (`web/frame-titlebar.js:26-49`):
- the path, then the tab strip, then `+`;
- on the full bar: the layout group `>_ { } ⇋ ▤ ⇄N` (L121-136), a spacer and
  `settings()`: the per-session pickers (network, tile API, `⧉ VM`, GPU;
  L145-178), ending in the tile-scoped `layerButtons` (`⬆ base update`, `⟲`;
  L205-213);
- on the degraded bar: `⋯` instead (L42-44), which opens the tools row
  (`toolsRow`, L100-102);
- last, `✕`.

This design adds the live-reload chip and the Reload now offer (tile-wide),
one entry per deployment in the existing tile API select (P24), and the `⇈`
layout button (§3.1).

### 2.1 The live-reload chip

A `<button class="lr">` showing the tile's live-reload state. It renders only
when the tile is out of the zero state. It renders what the State holds: a
reader's State carries only primary-scoped facts (§4.1), so a reader's chip
never names another deployment or counts files.

| State | Full bar | Degraded bar | Tooltip and `aria-label` |
|---|---|---|---|
| Zero state | — | — | — |
| Attached to the primary, other deployment state exists | `● Live reload: main` | `● main` | Live reload: main — every save reaches everyone using apps/crm. |
| Attached to a non-primary deployment | `● Live reload: dev` | `● dev` | Live reload: dev — saves reach apps/crm+dev. The primary, main, is pinned to c:3f2a1c9. |
| Paused, N files changed | `📌 Live reload paused · 3` | `📌 3` | Live reload paused by ana 12m ago — 3 files changed since c:3f2a1c9, which main runs. Reload now ships them to main once. |
| Paused, nothing changed | `📌 Live reload paused` | `📌` | Live reload paused by ana 12m ago — no changes since c:3f2a1c9. |
| Paused when the primary was protected | `📌 Live reload paused` | `📌` | Live reload paused when ana protected main — main is pinned to c:3f2a1c9. |
| Any of the above, a deployment's last deploy failed | the state's text, then `· deploy failed` (red) | the state's glyph, then `!` (red) | The last deploy to main failed; main keeps running c:3f2a1c9. [Reload now retries.] |
| A reader's view, the primary pinned | `📌 main pinned to c:3f2a1c9` | `📌 main` | main is pinned to c:3f2a1c9: saves in the work tree don't reach it. |

Rules:
- `N` is `State.workTree.changed` (11-contract §1.1), updated from the
  `deployments` event op `work-tree`, which carries the same count
  (11-contract §3.3). The browser never diffs, and the chip costs no request
  per save.
- "by ana 12m ago" comes from `State.liveReloadSince` (`by`, `at`). It reads
  "by ana (agent)" when an agent session's token made the change; that needs
  an `agent` flag on `liveReloadSince` (NP-10-10), and until it exists the
  suffix is left out.
- The cause comes from the last target's `lastDeploy.how`: `protect` gives
  "paused when ana protected main"; `deploy`, `promote` and `rollback` give
  the code-move headers of §12.1; `pause` gives the plain sentence.
- "deploy failed" shows while any deployment's `lastDeploy.result` is
  `failed`, and clears with that deployment's next `ok`. The tooltip names
  the deployment. "Reload now retries" appears only when the failed
  deployment is the last target and live reload is paused.
- On the degraded bar, names longer than 10 characters are cut with `…`; the
  tooltip carries the full sentence.
- Clicking the chip opens a `<bx-menu>` anchored under it, a bottom sheet on
  phones, exactly like the `+` launcher (`web/bx-frame.js:655-658`). Its items,
  in order:

| Item | Shown when | Does |
|---|---|---|
| header `Live reload` | always | — |
| the tooltip sentence, as a disabled item | always | — |
| `⇡ Reload now · 3` | paused | §5.2 row 3 |
| `Pause live reload` | attached | §5.2 row 1 |
| `Resume live reload on ▸`, a submenu: the last target first, then every other deployment except a protected primary | paused | §5.2 row 2, with resume's `deployment` |
| `Attach live reload to ▸`, a submenu of every other deployment except a protected primary | attached, two or more deployments | §5.2 row 4 |
| separator, then `⇈ Deployments…` | always | `open('deployments')` |

- An item the viewer may not use stays in the menu, `disabled`, with the
  server's reason as its `hint` (§4.2).
- Attach is never offered while live reload is paused: the server refuses it
  ("live reload is paused: resume it onto <name> instead", 11-contract
  §1.14), and Resume on ▸ reaches every deployment without first shipping the
  work tree to the last target.

### 2.2 The Reload now offer

On the full bar, directly after the chip:
`<button class="offer">⇡ Reload now · 3</button>`.
- It has an accent outline, the launcher's `.lresume` look
  (`web/frame-launcher.js:216-218`), and never the amber of `⬆ base update`,
  so the two offers can't be confused.
- It shows only when live reload is paused, `N > 0` and the state's
  `caller.can.reloadNow.ok` is true. In every other case Reload now lives only
  in the chip menu, disabled with its reason where that applies.
- The degraded bar has no separate offer. The compact chip's count is the cue,
  and the first action in its menu is Reload now.

Reload now always means the glossary's tile-wide act: checkpoint the work tree
and deploy it once to the deployment live reload last followed. Every viewer's
frame of that deployment reloads once. There is no "reload only my frame"
action. (This closes the first open question of
[research/ui-surfaces.md](research/ui-surfaces.md).)

### 2.3 The tile API select: a session's target (P24)

The target deployment belongs to a session (glossary). It is chosen in the
existing tile API select (`web/frame-titlebar.js:162-167`), which today offers
`🔌 tile API` and `⛔ no API`. There is no separate target picker.

- **Options.**
  - A tile in the zero state, or with a record and `main` as its only,
    unprotected deployment, keeps exactly today's two options, byte for byte.
  - Otherwise the select offers one entry per deployment the viewer may reach,
    then `⛔ no API`: `🔌 target: main (primary)`, `🔌 target: dev`, …
    (the glossary's "target: dev"). The primary comes first, then the others by
    name.
  - A protected primary is never listed. The select's `title` then adds "main
    is protected: terminals and agents can't call it". With the primary
    protected and live reload paused, `⛔ no API` is the only option.
  - The options are built from data, so they mark the choice with
    `live(.selected)`, as the comment above the pickers requires
    (`web/frame-titlebar.js:138-144`).
- **The default** for a new session is the server's (P24, NP-14-13): the
  primary; if the primary is protected, the live reload target; if live
  reload is also paused, the API is off. The launcher says which (§2.7).
- **Its value is the server's echo**, never the browser's guess: the session
  control frame's `deployment` (a name, absent for a session that follows the
  primary) and whether the API is on, handled in `_gotSession` like `net`
  (`web/bx-frame.js:730-745`). A request that named a deployment and got no
  echo came from an older xbind: the tab ends and says so (11-contract §7.4).
- **`🔌 target: main (primary)` means "the primary"**, a session that follows
  the primary and requests no deployment. A non-primary entry requests
  `deployment=<name>`. After a reassignment, the old primary appears under its
  name.
- **Changing it restarts the session**, as every picker does: the target is
  fixed for the session's life (NP-11-2). `_setApi` (`web/bx-frame.js:768`)
  takes the option's value (`off`, `primary` or a deployment name).
  - A shell goes through `_respawn`, whose confirm becomes "Restart this
    terminal calling dev?" (§5.2 row 18; `web/bx-frame.js:753-765`), and
    reconnects with `deployment=<name>`.
  - An agent goes through `restartAgent`, which resumes its conversation
    (`web/frame-launcher.js:95-124`), with `?deployment=<name>` on the restart
    route (11-contract §7.4).
- **`⛔ no API` also stops `bx`** in that session: every API call is
  unauthorized, deployment commands included. The select's title says so:
  "off = the shell can read and edit code, but every API call, bx included,
  is unauthorized".
- **When saves and calls go to different places**, the select's title gains
  "Saves reach dev; this terminal calls main." and the launcher shows the same
  line. The control never changes colour and never switches by itself: a
  terminal pointed at the primary on purpose stays pointed there.
- **Protecting the primary** restarts every session that targets it onto
  P24's default, or with the API off (NP-14-13). The tab's select then shows
  the new echo, and the terminal prints the server's note (§9).

### 2.4 Placement within D107's degrade rules

D107 ([../DECISIONS.md](../DECISIONS.md)): the bar is measured after every
render and resize (`fitBar`, `web/frame-titlebar.js:76-96`). It degrades when
it overflows and comes back once the window is as wide as it needed; `barKey`
(L61-62) lists what the width depends on.

| Bar mode | Where the new controls render |
|---|---|
| Full | `settings()` renders, in order: network, tile API (with the target entries), `⧉ VM`, GPU, **chip**, **Reload now offer**, `⬆ base update`, `⟲`. The chip and the offer render in **both** branches of `settings()` (`web/frame-titlebar.js:106-109`), so ended and history agent tabs and the empty window keep them. `⇈` renders in `layoutGroup`. |
| Degraded (under 640 px, the phone sheet, or measured overflow) | The **compact chip** renders in the title-bar row itself, between `+` and `⋯`, so the state never hides behind `⋯`. The tools row (`toolsRow`, L100-102) renders `layoutGroup` (with `⇈`) and `settings()` **without** the chip and the offer. |

- `barKey` gains: the attached name (or `""`), whether live reload is paused,
  `N`, the deployment count, whether the offer shows, whether a deploy failed,
  and each tab's target and API state (the select's label width). A change
  resets `_barNeed` (`web/bx-frame.js:239-240`) and fitBar measures again, as
  D107 requires.
- The compact chip is `flex: none` with `max-width: 12ch`. The tab strip
  absorbs the width, as today.
- D107's degrade order is unchanged: the path and the network label shrink,
  then the bar degrades, then tabs shrink to 56 px and the strip scrolls.

### 2.5 dragWindow's target rules

`dragWindow` ignores a pointerdown only on `button, select, .tab`
(`web/bx-kit.js:145-146`); pressing anything else on the bar drags the window.
Therefore:
- the chip, the offer and `⇈` are `<button>`s, and the tile API select stays a
  `<select>`;
- the glyph and the count are `<span>`s inside their button
  (`closest('button')` catches them);
- no element on the bar may put a click handler on a `span` or a `div`.

### 2.6 Glyphs

The taken glyphs and words are listed in
[research/ui-surfaces.md](research/ui-surfaces.md) (hazards) and
[research/terminology-census.md](research/terminology-census.md) (its
"live reload", "pause" and "pin" entries; "pin" is TAKEN, L330).

| Glyph | Means | Where | Why this one |
|---|---|---|---|
| `●` | runs the work tree (live reload attached) | chip, panel code column | bx-code already labels uncommitted work "● Working tree" (`web/bx-code.js:355`), the same object |
| `📌` | pinned to a checkpoint | inside the terminal window (chip, panel), and the frame chip, always beside the word "pinned" or "Live reload paused" outside the terminal window | "pinned" is the glossary term; not ⏸, which is Disable (`workspace-template/shell/menus.js:114`) |
| `⇡` | Reload now | offer, chip menu | same Arrows block as the `⇄` and `⇋` already on the bar; not ⟲, which resets the terminal layer (`web/frame-titlebar.js:211-212`), nor ⟳, which refetches the tile admin (`workspace-template/shell/bx-tile-admin.js:518`) |
| `⇈` | the Deployments layout, and the scaffold badges that open it | layout group, tile-menu line, card head, sidebar | unused; vertical, so it reads apart from the horizontal `⇄` beside it |
| `🛡` | protected primary | panel, `bx` | unused; 🔒 already means the namespace sandbox and read-only screens (`workspace-template/tiles/admin/tabs/runtime.js:419`) |
| `↗` | open in a new tab | panel | the apidocs tile's "spec ↗" precedent (`workspace-template/tiles/apidocs/apidocs.js:117`) |

"Pin" already means two other things builders see:
- a card pinned to the grid or unpinned into a window (▣/⧉,
  `workspace-template/shell/bx-canvas.js:294-295`; "Pin to the grid" /
  "Unpin into a window", `workspace-template/shell/menus.js:102`);
- builtin updates' `pin` and `unpin` modes (`docs/protocol.md:1425-1427`).

So `📌` never appears on a card head or a sidebar row, where it would read as
the card pin (those use `⇈`, §7), and every text outside the terminal window
says "pinned to c:…", never a bare "pinned".

This feature never uses ⏸, ⟲, ⟳, 🔒, ▶ (Enable, `workspace-template/shell/menus.js:112`),
▣ or ⧉ (VM, card pin). Every glyph is `aria-hidden="true"`, and its control's
`aria-label` carries the words.

### 2.7 The launcher

The empty window (`web/frame-launcher.js:152-184`) shows, above the session
cards, one line for the tile-wide state, modelled on the `.lbase` banner
(L160-164):
- paused: an amber banner, "Live reload is paused: 3 files changed since
  c:3f2a1c9, the checkpoint main runs.", with the `⇡ Reload now` button when
  the viewer may use it;
- attached to a non-primary deployment: a plain line, "Live reload: dev —
  saves reach apps/crm+dev; main is pinned to c:3f2a1c9.";
- the zero state, or attached to the primary: nothing.

When the tile has a record, each session card's subtitle names what a new
session calls, P24's default as the state reports it:
- "· target: main" (the primary);
- "· target: dev (main is protected)";
- "· tile API off (main is protected and live reload is paused)".

When the default differs from the live reload target, one plain line under
the cards reads "Saves reach dev; new sessions call main. Switch in the tile
API select after starting." The launcher has no target control of its own:
the tile API select is the one place to choose (P24).

## 3. The Deployments layout

### 3.1 The ⇈ layout button

- `layoutGroup` (`web/frame-titlebar.js:121-136`) gains a sixth button, `⇈`,
  on every tile, titled "deployments — live reload, deploy, promote, roll
  back". When the viewer's State lists two or more deployments it carries
  their count, `⇈ 2`, the way `⇄` carries the proposal count (L132-134); the
  count is in `barKey`. A reader's State lists only the primary, so a reader
  never sees a count. `.on` marks it active.
- It opens layout `'deployments'`:
  - `_layout`'s documented union (`web/bx-frame.js:95`) and `open(layout)`'s
    comment (L533-541) gain it, so the shell's tile menu can open it (§7);
  - `_setLayout` widens the window to 960 px for it, as for code, split and
    prs (L792-800);
  - `.panels` mounts `<bx-deployments>` lazily, like bx-logs and bx-prs
    (L843-844);
  - the per-user window pref records `'term'` in its place (NP-10-2), so a
    downgraded xbind never restores a layout it can't draw (`_restoreTerm`
    accepts any string, L328).
- **Test impact:** `hack/ui-harness/passes/agenttab.js:238` asserts exactly
  five `.lyt` buttons. It changes in the same change; 15-test-plan §7.4
  replaces the number with a `layouts` getter (NP-15-12).

### 3.2 Structure

`<bx-deployments component="apps/crm">` is a new shell-only `/vendor/`
element, defined in `web/bx-deploy.js`.
[/docs/frontend-kit.md](/docs/frontend-kit.md) lists it under Shell-only
modules. It follows bx-prs's shape, a side list and a main pane
(`web/bx-prs.js:41-95`, `:254-258`). It receives its host frame as a
property and asks every question through the frame's `_ask`/`_confirm`
(`web/bx-frame.js:714-725`). There is then one dialog at a time, and the
harness drives it with the existing `dialog`/`answerDialog` (§14).

```
┌ header ──────────────────────────────────────────────────────────────┐
│ 📌 Live reload paused · 3 files changed since c:3f2a1c9 (main)         │
│ (⇡ Reload now)  (Resume live reload on ▸)                             │
├ side, 230px ─────────────┬ main pane ─────────────────────────────────┤
│ tile-wide                │ overview · deploy log · logs ·             │
│ main  primary 🛡          │ registrations · view                        │
│   📌 c:3f2a1c9 · healthy  │                                            │
│ dev                      │ (the selected row)                          │
│   📌 c:7b19e02 · idle     │                                            │
│ + Add deployment…        │ actions row, sticky at the bottom           │
└──────────────────────────┴─────────────────────────────────────────────┘
```

- The **header** always shows the live-reload sentence (§12.1) and the
  live-reload buttons that fit the state: Pause live reload, Resume live
  reload on ▸, Reload now, Attach live reload to ▸. After a code move onto the
  live reload target it also shows **Undo** (§3.6).
- The **side list** starts with "tile-wide" (the primary, protection, outbound
  edges, caps), then one row per deployment (the primary first, then by name),
  then "+ Add deployment…".
- The **main pane** shows the selected row. The default selection is the live
  reload target, else the primary.
- The panel refetches the state on each `deployments` event for its tile, of
  every op 11-contract §3.3 defines (`record`, `deploy`, `work-tree`, `data`,
  `status`, `notify`, and the ops that carry a non-primary deployment's
  reloads and builds), debounced 250 ms like bx-code
  (`web/bx-code.js:267-272`). Events that name a non-primary deployment reach
  only admins, humans with at least write on the tile, and the tile's own
  sessions and that deployment's principals (05-model §8), so a reader's panel
  refetches only on primary facts.
- **bx-code needs the same signal.** It refreshes its work-tree diff only on
  `reload` and `build-ok` (`web/bx-code.js:268`), and a save while live reload
  is paused emits neither, only op `work-tree`. bx-code must also refresh on
  its tile's `deployments` op `work-tree`, or the Code panel goes stale exactly
  while live reload is paused.

### 3.5 Promote, with the diff first

A promotion onto the primary is the operation people fear most, so the panel
shows exactly what the receiving deployment gets before it asks.

1. "Promote dev → main…" in dev's overview opens the promotion view in the
   main pane, with `From` and `To` selects (defaults: this deployment and the
   primary) and the diff between what B runs and what B would receive, from
   `GET /api/xbin/deployments/diff` (11-contract §1.11):
   - A is pinned: A's checkpoint against B's checkpoint;
   - A follows the work tree: `to=work-tree`, which captures a checkpoint of
     the work tree when the view opens.
2. The diff renders through bx-code's exported `diffHTML` and `diffStats`
   (`web/bx-code.js:44`, `:70`), as bx-prs does (`web/bx-prs.js:15`), under a
   stats line: "c:3f2a1c9 → c:7b19e02 · 3 files, +40 −12". The two ids are the
   answer's `X-XBin-Checkpoint-From` and `X-XBin-Checkpoint-To`.
3. **What you saw is what ships.** Every code move sends the checkpoint its
   actor reviewed: `checkpoint` on deploy and roll back, `expect` on promote,
   reload now and reassignment. Onto a protected primary the server refuses a
   request without it (400), and a record that moved since the review answers
   409 (05-model §5, *Reviewed operations*). The panel always sends it, for
   every deployment, so the rule never surprises anyone.
4. If the work tree changes while the view is open (op `work-tree`), the view
   says "The work tree changed since this diff was taken." with a **Refresh**
   button. A promotion sent with the old `expect` answers 409, and the view
   refreshes the diff and says "The code changed since you reviewed it —
   review the new diff."
5. "Promote dev → main…" then runs the dry run and opens the confirmation
   (§5.2 row 7), whose message repeats the stats.
6. An empty diff reads "main already runs this code" and disables the button.

Deploy to X uses the same view when X is the primary. For a non-primary X it
goes straight to the confirmation, whose message carries the stats. Bar
actions (Reload now, Resume) have no room for a diff: their confirmation
carries the stats and says "The Deployments panel shows the diff."

### 3.13 The zero-state panel, and tiles that can't

## 4. Permissions in the UI

### 4.1 The state endpoint carries the viewer

Today the frame knows nothing about the viewer's level. A 403 from
`/ws/term/env` silently becomes `{}` (`web/frame-launcher.js:34`), because that
endpoint is terminal-gated (`termEnvGate`, `internal/server/server.go:335-352`).
The deployments state therefore comes from its own endpoint,
`GET /api/xbin/deployments?tile=<tile>` ([11-contract.md](11-contract.md)
§1.3), whose answer carries what the UI needs to render permissions:
- `caller`: the viewer's `level` (read, write, terminal, admin, or tile),
  `manager`, `readOnly` (view-as) and tile-level `can` with a `why` for each
  false (pause, resume, reload now, add, edges, protect);
- per deployment, `can` and `why` for every operation on it (open, deploy,
  promote to, roll back, attach, remove, reset, seed, vault copy, deliveries,
  alwaysOn, Run now, primary);
- `allowed`: what the tile itself may do (pause, have deployments), with the
  reason (isolation, chrome, an `xbin` capability, a cap), and `limits` (the
  caps).

**Readers get the State filtered to primary-scoped facts** (05-model §8):
live reload state as it concerns the primary, the primary's checkpoint and
deploy state, and protection. No non-primary deployment name appears, and no
count that reveals one. 11-contract §1.3 owns the exact shape. The panel then
shows the header sentence and the primary's row; every `can` is false with
its `why`; and the tabs that hold writers-only facts (the deploy log, diffs,
edges, registrations) read "Needs write access to apps/crm." There is no 403
to handle, and the frame never treats one as a silent `{}`.

Refusal texts name tile managers by role ("the tile's owner, its org's
admins, or a workspace admin", 11-contract §1.14). Naming the people, as D33's
who-can-approve hints do, would need the state to carry them (NP-10-9).

`loadTileState` (`web/frame-launcher.js:35-40`) also fetches the state when
the window opens and on every relist, and the frame refetches it on each
`deployments` event for its tile. The frame chip (§6.4) starts from the
components summary instead, so a zero-state tile costs no request.

### 4.2 Rendering rules

- A control that doesn't apply to the current state is **hidden** (Resume
  while attached; Seed on the primary).
- A control that applies but that the viewer may not use is **disabled**,
  never hidden. Its `why` becomes its `title`. Touch has no tooltips, so the
  reason also shows as a muted line under the panel's actions row, and as the
  `hint` of a bx-menu item. The VM toggle is the tooltip precedent
  (`web/frame-titlebar.js:194-199`).
- The UI never sends a request whose `can` is false.
- `can` is read again after every operation and every `deployments` event. A
  stale `can` is corrected by the server's refusal (§4.5).

| Viewer | Sees | May |
|---|---|---|
| read | the primary-scoped state: the chip's reader row, the header sentence, the primary's row; "Needs write access to apps/crm." on the other tabs; no frame chip | nothing; `open ↗` for the primary only |

### 4.4 View-as

A view-as session is read-only. The middleware refuses every non-GET with
"read-only: you are viewing the workspace as another user — exit the view (top
banner) to make changes" (`internal/server/impersonate.go:19`, `:33-40`). The
UI:
- computes nothing itself: GETs answer as for the viewed user (11-contract
  §0.5), so `caller.readOnly` is true and every `can` is the viewed user's;
- renders every action disabled. Where `can` says yes the tooltip reads "dev1
  may do this — you are viewing as dev1 (read-only)"; elsewhere it gives the
  ordinary reason. An admin sees exactly what dev1 could do, and no request is
  sent.

### 4.5 Refusals that still happen

A race, such as someone protecting the primary a second ago, can still produce
a refusal. Every request carries the state's `seq`, and code moves carry the
reviewed checkpoint (§3.5), so a moved record or moved code answers 409
instead of acting on stale facts (11-contract §1.2). Then:
- a 409 for a stale `seq` refetches the state, runs the dry run again and
  re-opens the confirmation with the new facts; a 409 for `expect` refreshes
  the diff (§3.5);
- any other refusal shows its `error` text (11-contract §1.14) verbatim,
  inside the section that asked, like the tile admin's `_do`
  (`workspace-template/shell/bx-tile-admin.js:163-174`), or, for a bar action,
  as `_confirm('Reload now was refused', error, 'OK')`, like restartAgent's
  failure (`web/frame-launcher.js:121`), and refetches the state;
- a refusal is never a silent no-op, and never only a toast.

## 5. Confirmations

### 5.1 Rules

- Every confirmation is a data-only `bx-dialog` spec passed through the
  frame's `_ask`/`_confirm` (`web/bx-dialog.js:9-20`). Its strings render as
  text only, D56's anti-phishing property. A dialog holds no markup, no links
  and no diff; the diff lives in the panel (§3.5).
- **Every confirmation renders a dry run of the exact request** (`dryRun:
  true`, 11-contract §1.2), and so does every `bx` summary (§8.1). The
  browser derives nothing:
  - the Code line comes from `impact.code`, and its `to` is what the request
    then sends as `checkpoint` or `expect`;
  - the Data line from `impact.data` and `stops`;
  - the Pauses line from `pausesLiveReload`;
  - the Affects line from `affects` and `reloads`;
  - every bracketed line in §5.2 from a fact NP-10-10 asks Impact to carry:
    seed size, mode and primary downtime; sibling claimants; the data an add
    joins; resources the new code declares; changes to the inbound surface;
    blocked and clamped edges; sessions that restart or lose their API; where
    live reload ends up; protection after a reassignment; secrets the new
    primary lacks.

  Until Impact carries a fact, its bracketed line is left out, never guessed.
  A dry run on a zero-state tile captures nothing and creates no checkpoint
  store (05-model §5), so its Code line names no checkpoint id.
- The message has up to six labelled lines, in this order, each present only
  when it says something (the dialog keeps line breaks, `web/bx-dialog.js:49`):
  - **Code:** what code goes where: checkpoints and file stats.
  - **Data:** what data moves, and resources the new code gains. Almost
    always "nothing moves".
  - **Edges:** what a new deployment may reach (Add only).
  - **Pauses:** live reload pausing, or a deployment stopping.
  - **Affects:** who notices: everyone using the tile, only the people using
    apps/crm+dev, or nobody now.
  - **Terminals:** sessions that restart, change target or lose their API.
- The request carries the state's `seq` and the reviewed checkpoint, so the
  confirmation is exact: if either moved, the answer is 409 and nothing
  happens (§4.5). This is D39's rule, "UIs confirm with the report", with the
  dry run as the report.
- The title is a question naming the effect. The OK button is the verb, never
  "OK" or "Yes". Cancel comes first.
- The OK button carries `danger: true` for removing a deployment, resetting
  data, a seed that replaces data, and reassigning the primary.
- A **required acknowledgement** is a checkbox field, and ticking it is what
  sends the route's `confirm` token (NP-11-5): removing a deployment
  (`erase`), resetting data (`erase-data`), seeding, including an add that
  seeds (`copy-data`), and reassigning the primary (`data-stays`). A
  reassignment whose target lacks secrets adds a second required box, which
  the UI checks and does not send. If the dialog resolves with a required box
  unticked, the host re-opens it with `error` set: "Tick the box to confirm."
- Escape, the backdrop and Cancel resolve `null`, and nothing happens.

## 6. Viewing non-primary frontends

### 6.1 In the panel: the view tab

The main pane's **view** tab embeds the selected non-primary deployment's
frontend as `<bx-frame src="apps/crm+dev" no-edit>`, the qualified `src` of
11-contract §2.5:
- Its iframe loads `/c/apps/crm+dev/`, and frame-info mints its bootstrap
  token with `?component=apps/crm&deployment=dev` (11-contract §7.2). No new
  attribute is needed; bx-frame's attributes stay the compatibility surface
  [/docs/frontend-kit.md](/docs/frontend-kit.md) promises.
- **Events follow rule C2** (05-model §8): `reload`, `build-*` and `status`
  only ever carry the primary's bare component, and a non-primary
  deployment's reloads and builds ride the `deployments` event, which names
  `deployment` (11-contract §3.3 names its ops).
  - The frame's `_event` (`web/bx-frame.js:366-369`) matches only its own
    component or a `/` child, so a `deployments` event (bare `apps/crm`) never
    reaches a frame whose `src` is `apps/crm+dev`. `_event` gains one line that
    hands every `deployments` event to `frame-deploy.js` before that test.
  - `frame-deploy.js` reloads a qualified frame when the event is for its tile
    and deployment and reports a reload, and paints its build overlay from a
    failed build. The overlay shows compiler output only when the event
    carries it (11-contract §3.4 decides who gets it); otherwise it reads
    "build failed — apps/crm+dev; the logs tab has the output".
  - The host's primary frame reacts only to bare events, as today
    (`isReloadTarget`, `web/events-socket.js:40-49`).
- It always wears its name as a label, `dev`, so it can't be mistaken for the
  primary (n8n's colour label that tells people where they are,
  [research/prior-art.md](research/prior-art.md), n8n).
- It never opens a terminal window of its own.
- **xbind's API is default-deny for it** (P26). Its frame token is bound to
  `dev`, and every `/api/xbin/*` route not classified for non-primary
  principals refuses it. A frontend that reads, for example, the workspace's
  tile list may show errors here that the primary never shows; the refusal
  text names the rule.

### 6.2 Full page, in a new tab

`open ↗` opens `/c/<tile>+<name>/` in a new tab with
`window.open(url, '_blank')`, like the shell's `openFullPage`
(`workspace-template/shell/bx-shell.js:906`). The address bar shows the
deployment. v1 draws nothing into the tile's own document (the repo's one
sanctioned HTML transform, CLAUDE.md); a tile that wants to label itself reads
`xbin.deployment` (11-contract §6). Open question 1 asks whether the injected
client should draw a corner label.

### 6.3 Why not as shell cards in v1

- Layouts key tiles by path: `_isOpen`
  (`workspace-template/shell/bx-shell.js:996`) and the canvas `repeat`, keyed
  by `o.path` (`workspace-template/shell/bx-canvas.js:419`, `:424`). A second
  card for `apps/crm` would break old shells, so a card would have to be
  stored as `apps/crm+dev`.
- That entry has no `/api/xbin/components` row: an old shell would draw it
  with no runtime dot, no tile menu and no sidebar row. The iOS app reads
  layout paths (`native/ios/Packages/XbinCore/Sources/XbinCore/Client/Catalog.swift:187`)
  and resolves tiles by `/` boundaries (`.../Client/TileLoading.swift:74-79`),
  so it would find no tile for it. After an xbind downgrade the entry points
  at nothing.
- Org screens are shared (D55), so one user's `+dev` card would reach every
  member's shell, old or new, and an app that lags months behind.

v1 therefore has no deployment cards: the view tab and the full-page tab cover
viewing. A later rung can add cards once shells and the app understand
qualified layout entries.

### 6.4 The frame chip

bx-frame's `.frame-wrap` (`web/bx-frame.js:818-829`) is the only
binary-served surface drawn over a tile, so it carries the one ambient
indicator that reaches old shells. `web/frame-deploy.js` draws it
([13-surfaces.md](13-surfaces.md)).
- **For whom:** viewers with terminal level on the tile, the people whose
  saves are affected. The state's `caller.level` says so (11-contract §1.1),
  fetched only when the components summary says the primary is pinned. Read
  and write viewers see a normal app and no chip.
- **When:** the frame shows the primary, and the summary says the primary is
  pinned. Never in the zero state, and never while live reload is attached to
  the primary.
- **What:** a small `<button class="dchip">` at the top right, left of the
  edit button's spot, at 55 % opacity: the edit button's quiet manners
  (`web/bx-frame.js:126-132`). At rest it reads `📌 pinned`, never the glyph
  alone (§2.6). Hover or focus expands it to "main pinned to c:3f2a1c9 · live
  reload paused", or "main pinned to c:3f2a1c9 · saves reach dev". It carries
  no file count. A click opens this tile's terminal window on the Deployments
  layout.
- **Touch:** on `(max-width: 820px)` or `(pointer: coarse)` the chip keeps its
  small look but gets a 44 px hit area (an invisible `::before` inset), the
  sheet rule of §13.
- The view-tab frame (§6.1) shows its deployment's name instead, always.
- **Data, in two steps:**
  - the primary summary on the tile's existing `/api/xbin/components` row
    (11-contract §8 owns its fields: the primary's name, whether it is pinned,
    whether it is protected). It holds only primary facts, for every caller
    (05-model §8), and
    is absent for zero-state tiles, so their rows stay byte-identical and cost
    nothing (the `native`, `origin` and `sandbox` precedents,
    `internal/server/api.go:130-160`). The frame reads it through
    frame-info's per-page cache (`web/frame-info.js:44-51`), updated from
    `deployments` events and refetched when the page becomes visible;
  - only for a tile whose primary is pinned, one `GET /api/xbin/deployments`
    per page: its `caller.level` decides whether the chip shows, and the
    state gives the checkpoint and the hover text's cause.
- The chip sits inside `.frame-wrap`, so hovering it counts as hovering the
  tile; the reload-focus rules (`web/bx-frame.js:419-461`) are unaffected.

## 8. bx CLI

[11-contract.md](11-contract.md) §9 is authoritative for the commands, flags,
output, prompts and exit codes, and this section adopts them verbatim. The
commands are 11-contract §9.2's: `bx live-reload [pause|resume|now|attach]`,
`bx deployment ls|add|rm|primary|protect|seed|reset|vault-copy|set|edge|run-now|log|diff`
(deliveries and alwaysOn are `bx deployment set` flags), `bx deploy`,
`bx promote` and `bx rollback`. They sit in `cmd/bx/livereload.go`,
`cmd/bx/deploy.go` and `cmd/bx/deployment.go`, with shared plumbing in
`cmd/bx/deployclient.go`, and are dispatched through `moreCmds`
(`cmd/bx/native.go:28-32`) because `cmd/bx/main.go` is at its 1150-line
budget. This section fixes only the words on top of that contract.

### 8.1 What bx prints before it acts

Every changing command prints its impact report, a dry run of the request,
before it asks or acts (11-contract §9.1). The report uses §5.1's labelled
lines and the same facts the panel uses, and bx then sends the dry run's
`impact.code.to` as the reviewed checkpoint. A code move onto the primary
always names its audience.

```
$ bx promote apps/crm dev main
Promote dev → main (the primary of apps/crm)
  Code     main runs c:7b19e02 (the work tree at 14:02) · 3 files, +40 −12 against c:3f2a1c9
  Data     only code moves — main keeps its data, secrets, cron jobs and routing
  Affects  everyone using apps/crm: frames reload once; WebSockets and SSE drop at the 30 s drain
proceed? [y/N] y
apps/crm: promote 44 dev → main c:7b19e02 … build … start … swap … ok (38s)
```

- The words are §12's: "pinned to c:3f2a1c9", "work tree", "started empty".
- Glyphs appear only in human output. `--json` prints the route's answer
  verbatim and nothing else on stdout (11-contract §9.1).

### 8.2 Prompts and `--yes`

- On a terminal, bx asks `proceed? [y/N]`, as `bx owner --transfer` does
  (`cmd/bx/org.go:430-436`).
- Without a terminal, a command that needs confirmation (11-contract §9.1
  says which) prints the report, names `--yes` and exits **4** (not
  confirmed). bx already checks `term.IsTerminal` (`cmd/bx/passphrase.go:16`).
- `--yes` skips the prompt, never the report, and also sends the route's
  `confirm` token.
- Agents run bx without a terminal, so an agent can't ship without writing
  `--yes`: its statement that the user asked (§10).

### 8.3 XBIN_DEPLOYMENT and targets

- Read commands (`bx status`, `bx logs`, `bx deployment log`) default to
  `$XBIN_DEPLOYMENT` when the tile is `$XBIN_COMPONENT` (DR3, 11-contract
  §0.4), and every such output names the deployment ("apps/crm+dev").
  Self-scoped writes (`bx vault set`, cron jobs, subscriptions) act on the
  session's bound deployment by the server's rule (DR1).
- A command that moves code never takes its target from the env: `bx deploy`
  and `bx rollback` need `--to`, and `bx promote` names both deployments.
  `bx live-reload resume` defaults to the last target, which its report names.
- `bx deployment ls` marks the row the session targets with "← this
  terminal".
- Only backend calls to `/api/<tile>/…` are confined to the session's target
  (P12). xbind's own reads, such as logs and status, take any deployment of
  the tile the caller may read.
- In a session whose tile API is off (§2.3), every bx call is unauthorized.

  today's scoped-terminal hint (`cmd/bx/main.go:264-272`; 11-contract §9.1).
- Exit codes are 11-contract §9.1's, verbatim:

  | Exit | Meaning | An agent reads it as |
  |---|---|---|
  | 0 | done: the deploy finished `ok`, nothing needed doing, a dry run, or `--no-wait` and the request was accepted | — |
  | 1 | failed: a deploy that ran and failed (the deployment keeps its previous code), an invalid state, a network error, any other refusal | read the message, fix, retry |
  | 2 | usage | fix the command |
  | 3 | refused by authority or policy: a `Can` of kind `authority` or `policy`, or HTTP 403 | not yours to do: tell the user who can (the message names them) |
  | 4 | not confirmed: declined, or a guarded command with no terminal and no `--yes` | ask the user |
  | 5 | still running when bx stopped waiting; `bx deployment log` shows it | check later |
  | 6 | this xbind has no tile deployments | don't retry here |

- Today bx exits 1 on every error (`cmd/bx/main.go:105-108`) and 2 on usage
  (L175). Existing commands keep that.

### 8.5 Existing commands

- `bx status` prints a `deployments:` line when the tile has a record
  (11-contract §9.3), in §12.1's words: `live reload paused · 3 files changed
  since c:3f2a1c9`, or `live reload: dev · main pinned to c:3f2a1c9`, plus the
  session's target. A zero-state tile's output is unchanged.
- `bx logs` streams a named deployment's log through
  `GET /logs?deployment=` (11-contract §9.3), not the direct file read, which
  already fails in isolated terminals
  ([research/side-findings.md](research/side-findings.md) #22).
- `bx builtin update` and `bx restore` print flow E's line (§3.14) when the
  primary is pinned.
- `bx ls` is unchanged. It lists tiles, never deployments.

## 9. Terminal notices

A grey line appears in the open terminals of a tile when its tile-wide state
changes, so someone typing in a terminal learns that their saves stopped, or
started, reaching somebody. The framing is exactly netNote's,
`\r\n\x1b[90m[…]\x1b[0m\r\n` (`web/bx-terminal.js:634-637`).

Mechanism (NP-10-1): the frame's `frame-deploy.js` handles the `deployments`
events for its tile, op `deploy` when a result is final and op `record` when
`liveReload`, `primary` or `protectedPrimary` changed (11-contract §3.3), and
calls a new public `note(text)` on each of its `<bx-terminal>` elements
(bx-terminal is at 713 of 900 lines). `note()`:
- writes at once while the terminal shows its normal buffer;
- while a full-screen program holds the alternate buffer (vim, less, a TUI),
  keeps only the latest note and writes it when the program exits, so no
  screen is ever corrupted;
- skips the tab whose own session performed the act, named by the event's
  `session` (11-contract §3.3), where bx has already printed the result.

Events that name a non-primary deployment reach only viewers with at least
write on the tile (05-model §8), which every terminal user has.

**The session's own first line (NP-10-14).** When a session starts with a
target other than the primary, or with the tile API off by P24's fallback,
the server's session control frame carries a note, and bx-terminal writes it
exactly as it writes netNote (`web/bx-terminal.js:634-637`):
"[this terminal calls apps/crm+dev]", "[tile API off: main is protected and
live reload is paused]", or, after protection restarted it, "[this terminal
restarted when ana protected main — it now calls apps/crm+dev]".

Agent tabs get no transcript lines: agents learn the state from bx (§10). The
iOS app's terminal gets none either (§11).

| Event | Line |
|---|---|
| paused | `[live reload paused by ana — main is pinned to c:3f2a1c9; saves no longer reach it]` |
| resumed | `[live reload resumed on main by ana — saves reach main again]` |
| attached elsewhere | `[live reload attached to dev by ana — saves reach apps/crm+dev; main is pinned to c:3f2a1c9]`, plus ` — this terminal still calls main` when the tab's target differs |
| a deployment added, or the tile's first record | the line above, plus ` — new terminals get the xbin-deploy remote` |
| code moved (deploy, promote, roll back, reload now) | `[main now runs c:7b19e02 — promoted from dev by ana]` |
| a code move failed | `[deploy to main failed — main keeps running c:3f2a1c9; the Deployments panel has the output]` |
| primary reassigned | `[dev is now the primary of apps/crm (by ana) — it serves dev's data]` |
| protection changed | `[main is protected by ana — only tile managers change its code]` |
| the tab's target removed | `[deployment dev was removed by ana — this terminal's API calls fail until you switch it in the tile API select]` |

Op `work-tree` (saves while live reload is paused) never writes a line. A line
can land between a prompt and a half-typed command, exactly as the existing
`[reconnecting…]` line does (`web/bx-terminal.js:676`); the command stays in
the shell's buffer and only its display is split.

````md
## Tile deployments: when a save doesn't reach everyone

Most tiles have none: every save reaches everyone (live reload). A tile's
developers can change that per tile:

- **Live reload paused:** saves change the files and nothing else. The tile
  keeps running a pinned checkpoint until someone presses Reload now.
- **Tile deployments** (`main`, `dev`, …): named runtimes of one tile, each
  with its own code, data and secrets. Live reload follows at most one of
  them; the others run pinned checkpoints. The **primary** (usually `main`) is
  what everyone and everything else reaches; the others are only at
  `/c/<tile>+<name>/`.

Check before you test or debug:

```sh
bx live-reload        # where saves go ("main — every save reaches everyone (no deployments)" = none)
bx deployment ls      # names, primary (🛡 = protected), code, status; "← this terminal" is your target
```

- Saves reach the **live reload target** (or nothing while paused). Your API
  calls and `bx status`/`bx logs` reach **your target**, which is the primary
  unless the user picked another in the terminal's tile API select. They can
  differ: check both before deciding a fix "didn't work".
- **You can't switch your own target.** To call a non-primary deployment, ask
  the user to pick it in the tile API select (the session restarts). Reads
  work without switching: `bx status <tile>+dev`, `bx logs <tile>+dev`. If bx
  answers "unauthorized", this terminal's tile API is off.
- **Committing never deploys.** Keep committing often (the commit policy
  above); a commit changes nothing anyone runs.
- **Don't `bx deploy --to` the live reload target**: saves already reach it,
  and a deploy onto it pauses live reload.
- **Shipping to the primary is a deliberate act.** Run `bx deploy --to main`,
  `bx promote <tile> dev main`, or `bx live-reload now` while live reload last
  followed the primary, only when the user asked you to ship — never as part
  of committing, testing or tidying up. Try the change on a non-primary
  deployment first. Without a terminal bx prints what will change and stops
  (exit 4); `--yes` says the user asked.
- **A large change on a tile that has no non-primary deployment:** pause live
  reload, build and test in the terminal, and resume when done. Resuming, like
  `bx live-reload now`, ships the work tree to whoever live reload followed,
  so do it only when the user asked. Leave paused live reload that someone
  else paused (`bx live-reload` says who) unless the user asked.
- **A refusal is not yours to work around** (exit 3) — for example "the
  primary of apps/crm (main) is protected: only tile managers change its
  code". Stop and tell the user who can (bx says who); never look for another
  way in.
- **A new deployment starts with empty data** and secret names only. Fill it
  with synthetic data through its own API, from a session that targets it.
  Copying the primary's data or secret values into it is a tile manager's act.
- **Non-primary deployments read other tiles' primaries and never write to
  them.** Writer roles are clamped to reader, so, for example, LLM turns
  through `apps/llm-gw` are refused there. Edges that can't be limited to
  reading are blocked: an agent tile's sandbox managers (custom role
  `consumer`) are unreachable from its non-primary deployments, so test
  sandbox work from the primary.
- To fix the primary while the work tree holds unfinished work:
  `git fetch xbin-deploy`, `git checkout -b hotfix deploy/main`, fix, commit,
  and `bx deploy --to main` once the user says ship. If `git fetch xbin-deploy`
  fails, the terminal predates the tile's deployments: open a new one.
- "3 fast crashes ⇒ failed" and "status resets on restart" hold per
  deployment. A pinned deployment recovers through a deploy, not a save.
````

## 11. The native app

v1 ignores non-primary deployments, and the primary works as today.
- **Tiles** come from `/api/xbin/components`, which gains no rows (§6.3). Its
  `native` field describes the primary's code (05-model §6), so the app opens
  a native document only when what the primary runs declares one.
- **Pages:** `/c/<tile>/` and `/c/<tile>/?native=1` serve the primary, pinned
  or not.
- **Reloads:** a successful swap on the primary emits one ordinary `reload`
  for the tile, only when the primary's code changed, so an open view reloads
  once. Saves while the primary is pinned emit nothing (05-model §8).
- **Events:** under rule C2 no old event type ever names a non-primary
  deployment, so the app's reload targeting
  (`ReloadTargets.covers`, `native/ios/Packages/XbinCore/Sources/XbinCore/Client/Events.swift:162-166`)
  never sees one. The new `deployments` type is unknown to the app and becomes
  `.other` (`Events.swift:79-80`), so it reloads nothing, whatever it names.
- **Notifications** from non-primary deployments are never pushed (P13).
- **Terminal:** the app's terminal (`native/ios/App/Terminal/TerminalController.swift`)
  opens sessions without a `deployment` parameter, so it gets P24's default:
  the primary; the live reload target when the primary is protected; the tile
  API off when live reload is also paused. It checks no echo, shows no
  target, and ignores fields and control ops it doesn't know
  ([/docs/compat.md](/docs/compat.md) rule 10), including the session note of
  §9. Inside the session, `bx deployment ls` and `$XBIN_DEPLOYMENT` tell.
- **On a phone**, a developer uses the web shell through the app's "Open in
  Safari" (`native/ios/App/Tiles/TileScreens.swift:95`). The terminal window's
  sheet there has everything (§13).
- A later rung can add a deployment switcher, a target display in the app's
  terminal and native documents for non-primary deployments.

### 14.4 Restoring state after passes

Live-reload state belongs to the tile and outlives a pass, so a failed pass
could leave later passes (reloadFocus, agentTab) running against a changed
tile. Every deployment pass must:
- change state only on its own fixture (`apps/reloady` or `apps/deployy`;
  `apps/crawler` is used only for refusals, which change nothing);
- call `resetDeploys(ctx, tile)` **at its start and in `finally`**. Through the
  API, as the tile's manager, it reassigns the primary to main, unprotects it,
  sets every edge back to `default`, removes every other deployment and
  resumes live reload on main, sending the `confirm` tokens and reviewed
  checkpoints those routes need. It then asserts that the state answers
  `record: false`: P5's "opting out returns to it" doubles as the check;
- restore the fixture's `index.html` bytes;
- end its sessions and delete the `term:<tile>` pref, as today's passes do.

## Open questions

1. Should the injected client draw a small corner label, `+dev`, in
   non-primary top-level documents? It would help people who keep a
   deployment's tab open for days, but it is new tile-visible UI inside
   documents xbind doesn't own (§6.2).
2. Resolved: the chip's count is `State.workTree.changed`, updated by op
   `work-tree` (11-contract §1.1, §3.3), so it costs no diff.
3. Should an agent tab get a transcript line when live reload moves away from
   its target, or is bx enough (§9)?
4. Should the sandbox shell's prompt show `+dev` when `XBIN_DEPLOYMENT` is set,
   so every client, the iOS app's terminal included, shows the target? The
   seeded `.zshrc`/`.bashrc` reach only new homes, so it would need a prompt
   hook xbind injects per session.

## Divergences from the model

1. Resolved by P24: a protected primary is never a session's target, and the
   last fallback is "API off" (NP-14-13).
2. Resolved by P24: a session's target is fixed for its life (NP-11-2).
3. Resolved by the spine: the glossary's Spellings row now reads "started
   empty" / "seeded from main · <when>".
4. Resolved by the spine: the glossary's deploy log lists pausing and
   attaching live reload, and 11-contract owns the full `how` list.
5. Resolved by the spine: 05-model §10 gives Run now to terminal level.
6. Resolved by ruling C2 and 05-model §8: a failed deploy onto a pinned
   primary paints no overlay.
7. **Set limits has an authority row but no operation.** 05-model §10 makes
   "set a deployment's resource limits" a tile manager's act (P22), and §6
   says limits are per-deployment settings, but §5's operation table has no
   row for it and 11-contract has no route. This document designs the UI
   (§3.8, §5.2 row 20). Recommended fix: a "Set limits for Y" row in 05-model
   §5 (manager, human session, never above the tile's ceilings) and a
   `POST /deployments/limits` route in 11-contract (NP-10-10).

## New proposals

- **NP-10-1 — Terminal notices are written by the browser.** bx-terminal gains
  a public `note(text)`, called by `frame-deploy.js` on the `deployments` ops
  `deploy` (final results) and `record` (when `liveReload`, `primary` or
  `protectedPrimary` changed). It defers while the alternate buffer is active,
  and skips the tab named by the event's `session`. No `/ws/term` change is
  needed, and `internal/term/term.go` is at its 950-line budget.
- **NP-10-2 — The `'deployments'` layout isn't persisted.** The per-user
  window pref records `'term'` in its place, so a downgraded xbind never
  restores an unknown layout into an empty window.
- **NP-10-3 — One pure module holds every string.** All §12 strings and the
  state-to-controls logic sit in `web/deploy-state.js`, which imports nothing
  and is pinned by `hack/deploy-state.test.mjs`. bx's strings follow the same
  table.
- **NP-10-4** — resolved by the glossary's Spellings row; the "· reset <when>"
  suffix stays a wording detail of §12.1.
- **NP-10-5** — resolved by ruling C2 (05-model §8).
- **NP-10-6** — resolved by ruling 12: 11-contract §9.1 decides which commands
  need `--yes`.
- **NP-10-7** — withdrawn by ruling 12: refusals exit 3, and 6 means no tile
  deployments (11-contract §9.1).
- **NP-10-8 — The ▤ logs layout follows the active tab's target.** bx-logs
  gains an optional `deployment` attribute (`observedAttributes`,
  `web/bx-logs.js:61`), sent as `/logs?deployment=`. The Deployments panel's
  logs tab uses the same element for the selected row.
- **NP-10-9 — The deployments state names the tile's managers.** Listing the
  user-owner and the owning org lets tooltips and refusals say who to ask, as
  D33's who-can-approve hints do; 11-contract §1.14's texts name only roles.
- **NP-10-10 — The facts the confirmations and the panel render.**
  11-contract §1.1 extends:
  - `Impact` with: `seed` (`bytes`, `mode`: online or stopped, `required`
    with its reason, `primaryDownFor`); `claimants` (sibling tiles sharing
    the namespace); `joins` (the state of the namespace an add joins, the
    deployment it was seeded from, and when); `newResources`; `inbound` (changes to what the tile exposes
    or provides, onto the primary); `edges` (`blocked` and `clamped` ids with
    reasons, and the network's effect); `sessions` (`restart`, `retarget`,
    `loseApi` counts); `liveReloadAfter`; `protectedAfter`; `missingSecrets`
    (the reassignment preflight of 08-data §10);
  - `Deployment` with `resources` (declared, only-here, kept-undeclared) and
    `limits` (effective values and whether each is the tile's default);
  - `Edge` with `refused` and `clamped` counters (05-model §7);
  - `liveReloadSince` with `agent`;
  - a manager route that sets a deployment's limits (Divergence 7).
- NP-10-11 and NP-10-12 are left unused: 11-contract's older text cited those
  numbers for things this document never proposed.
- **NP-10-13 — Flow E says where an applied change lands.** When the primary
  is pinned, bx-prs's apply hint, `bx builtin update` and `bx restore` print
  one line naming the primary's checkpoint and where the work-tree change
  reaches (the live reload target, or nothing while live reload is paused).
  The manager tile's Updates action may show it as optional garnish.
- **NP-10-14 — A session says its own target.** When a session starts on a
  non-primary target, or with the tile API off by P24's fallback, the session
  control frame carries a note, and bx-terminal writes it like netNote (§9).
  It is how a terminal restarted by protection learns why.
