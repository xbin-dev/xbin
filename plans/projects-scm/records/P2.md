## Changelog text

**Big tasks, upgrades and pull requests** (agent template, API.md §Big
tasks, upgrades and pull requests): a task created `big` works in a
sandbox of its own, cloned from a snapshot of the project's sandbox the
agent takes while it is quiet (or made fresh from the same image), emptied
of other tasks' checkouts and of every credential, with its own credential
and the repos fetched; it is deleted when the task is cleaned up (unless
`bigTasks.keepFork`). "Make this a project…" (`GET
/runs/{id}/project/detect`, `POST /runs/{id}/project`) turns a
conversation with a sandbox and git clones into a project whose first task
is that conversation, on a new branch, its clones adopted and never
removed. `POST /runs/{id}/task/pr`, and `policy.autoPR` when a task comes
to rest, push the task's own branch — never a default branch — and open a
pull request per repo. Additive: no new table; an older build leaves an
upgraded conversation out of its conversation list (reachable by link and
search).

## Decision text

- **Forks are made inside `prepare`.** `provisionFork` is synchronous by
  the seam, and P1's `prepare` counts any error as an attempt, so a fork
  can't be a job prepare waits on; the fork is made, cleared, given its
  credential and fetched in that call (a fresh fork's clones run there in
  background execs it polls, holding one of the worker's four slots). The
  `fork` job kind is the fork's deletion.
- **No live token in a snapshot or a fork:** the snapshot scrubs every
  project's credential in the sandbox first (the gate writes fresh ones
  when a task next needs them), and a fork removes `H/.config/xbin-scm`
  before anything runs in it, then gets its own credential through K's
  gate. Not chosen: relying on the fork's removal alone (the snapshot
  would keep live tokens at the manager until they expire).
- **Quiet is what the agent knows plus what the manager says:** the
  spec's three conditions, a conversation or workspace job at work there,
  and any exec the manager runs (a person's terminal, which no table of
  the agent's holds).
- **A fork base costs a stop:** taken once the repos are ready, then only
  when a day old *and* worked in since; the loop's own job never waits
  (a waiting job keeps the process up); a person's ask waits up to 30 min.
- **A registry of forks** (a setting per fork) rather than a table: a fork
  must outlive its task's row (a deleted project) to be deleted, and the
  create's choice (snapshot or fresh, its clientId) must survive a retry.
- **The pr job pushes one refspec**, `refs/heads/<branch>:refs/heads/<branch>`,
  from checkouts on that branch only, and refuses a default branch — the
  token's write scope covers it, and an upgraded conversation's branch is
  the person's.
- **Auto-PR** acts for repos without an open pull request and only after a
  turn that rests idle or done; once a pull request is open the task
  pushes to it itself.
- **An upgrade fails closed:** a conversation that held internal data, a
  shared one or a busy one is refused; `branch` defaults to `new`; `keep`
  on a default branch is refused. Not chosen: copying a shared
  conversation's sharing onto the project (Owner question).

## Owner questions

- **Scrubbing before a snapshot.** Built: every project's credential in
  the sandbox is scrubbed (revoked, files emptied) before a fork base is
  taken, and re-minted when a task next needs it — no snapshot holds a
  live token. The cost: a re-mint per project per snapshot (daily at
  most). The alternative is to rely on the fork removing what it
  inherited, leaving live tokens in the snapshot at the manager until
  they expire (≤ 1 h bot, hours for a person's).
- **Upgrading a conversation that has held internal data.** Built:
  refused (409 `class-internal`), as a task never has internal reach and a
  task pushes to the provider. Allowing it would need the conversation's
  `heldInternal` to be dropped, which nothing else does.
- **Upgrading a shared conversation** (unpartitioned agents). Built:
  refused — unshare, upgrade, share the project. The alternative copies
  the conversation's visibility and members onto the project (subject to
  P1's `sandbox-shared` rule).
- **Fork bases for every project.** Built per the spec: every active
  project with `bigTasks.mode: fork` (the default) gets one after its
  first warm-up, refreshed when a day old and worked in since — each a
  brief stop of a quiet sandbox. The owner may prefer to take the first
  one only when a project's first big task is created (that task would
  then be fresh).
