## Changelog text

> **Projects on the web.** The agent's sidebar has a **Projects** entry
> (with the tasks that need you): the list of your projects (and team
> ones), each project's **board** — a column per state, a card per task
> with its branch, pull requests and CI — **New task** (small or big, the
> project's default or a coding agent by name, which repos) and **From issues…** (a
> task per picked issue), and its **Settings**: status (sandbox, repos,
> credentials — never a token — jobs, warnings), repos and their setup
> scripts, every policy key, members, archive and delete. **New project**
> picks the provider, the repos you can reach, a sandbox and the basics,
> and signs you in to the provider (its device code shown to you only); at
> a partitioned agent's shared space it makes a team project's definition,
> shared, its seed sandbox optional. A
> task's conversation shows its branch and pull request, **Open PR**, the
> way back to its project, and while its workspace is prepared a card with
> each step, Retry, and the sign-in it waits for. Links: `#proj`,
> `#proj=<id>`. The native view follows.

## Decision text

- The new-project "dialog" is a form in the Projects page (as Automations'
  forms are), not a modal: it has an address-free state the native view
  mirrors as a screen, and the repo picker and sandbox sections need the
  room.
- "Open PR" is shown only once the backend is known to have
  `POST /runs/{id}/task/pr`: probed with a `GET` of that path (405 where a
  POST-only route is mounted, the mux's plain 404 where it isn't), once
  per home — a POST would open a pull request to find out. A click that
  meets the plain 404 hides it too. Not chosen: hiding it until a POST
  answers (it can't be learnt without opening one), or a capability flag
  (none exists in §7).
- After the person's sign-in from a task's card is done, the task is
  refreshed once (`POST /runs/{id}/task/refresh`), so the gate looks at the
  credentials at once rather than at its next wake.
- Issue bodies in the picker are clipped to 240 characters, drawn as plain
  text in a dashed "untrusted" frame, with the tracker named; the backend
  already redacts and clips them (2 KiB).
- Project modules bring their own `<style>` (as `harness-board.js` does):
  index.html stays at its one bounded line.
- A policy edit is saved at the version its draft was read at, and a
  rename or visibility change at the version shown when it began — never
  at whatever was read since (a `project` event reads the project again
  while the owner edits). On a 412 the draft is rebuilt from the project
  read again with the owner's changed keys set on it, so both changes show
  and the next Save sends both at the new version. Not chosen: re-sending
  the old draft at the new version (it would revert the other change).
- "Who works on it" offers the project's default, said as what it does,
  and the catalog's coding agents by name; "the built-in agent" is named
  only where the default resolves to it (policy `engine: builtin`, or no
  coding agent available). `TaskSpec` (S0's, frozen) can name a coding
  agent or nothing, so an explicit built-in pick can't be sent where the
  policy's default is a coding agent (Owner questions).
- The new-project form at a partitioned agent's global instance makes a
  team definition: `kind: "team"` with `share` always sent (team
  visibility by default, or private with the members added next), and the
  seed sandbox optional (none by default — a seed holds no credential).

## Owner questions

- Should `TaskSpec` gain an explicit built-in pick (e.g. `agent:
  {provider: "builtin"}` or `engine: "builtin"`), so a person can ask for
  the built-in agent on a project whose policy picks a coding agent
  (`proj.task.agent`: "who answers: built-in or a coding agent")? Today
  `Agent == nil` means `policy.engine`, and `auto` picks the person's last
  coding agent; U1 names the built-in agent only where that is what
  nothing means. `projects_types.go` is S0's, so this is the lead's call.
