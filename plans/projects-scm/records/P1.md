## Changelog text

**Projects** (agent template, API.md §Projects): a project is a coding
sandbox, its repos (bare bases in the sandbox, cloned from the bound scm
provider), a policy and task conversations. `POST /projects` checks the
provider, the repos (the scm bot rule where the home works as the bot)
and the sandbox, then prepares the workspace in the background; `POST
/projects/{pid}/tasks` makes a task — its own conversation with a git
worktree per repo on its own branch, a range of ports, the repos' setup
run for it — answered by the built-in agent or a coding agent. A task's
turn waits at the workspace gate until its checkout is ready, at most
`maxTasks` tasks work at once (the rest wait in the project's queue), and
what a task pushes or opens as a pull request is noticed after each turn.
Tasks never run with internal reach; a project's conversations share its
sharing (its owner takes part in every task) and stay in its space, and a
shared project has its sandbox to itself. Cleanup refuses unpushed work unless the
conversation's owner forces it. Additive: an older build leaves the new
tables alone and lists no task conversations among its chats.

## Decision text

- **One worker per engine owner, jobs in the database:** epoch-fenced
  claims and execs found again by `clientId` survive a handover; the
  scripts take every value through env.
- **The gate parks, it never consumes:** a parked task keeps its inbox;
  the park ends in the gate itself once the workspace is ready (the run
  rests and the pass goes on), so no wake row is queued — none can be left
  over — and a workspace change pokes the run so the park follows it. A
  turn in flight is never parked.
- **Slots count runs, not workspaces:** a task holds a slot while its run
  is active, parked at the gate or waiting for a person (V5), and from the
  moment input is delivered to it until it takes it up (so pumps back to
  back never overfill); a person's own message bypasses the queue.
- **Archiving holds, it doesn't fail:** an archived project's workspace
  jobs wait untouched and count as nobody's work; a turn waiting for its
  workspace is shelved back into the queue's head and its run rests; the
  project made active again picks everything up where it stood.
- **A project's sandbox is used with its owner's authority** (the
  binding of every task, as the repo and prepare jobs already were): a
  participant creates tasks without being the sandbox's member. The owner
  is a participant member of every task someone else created, so that
  binding holds at every tool call, and the owner acts on every task.
- **A shared project has its sandbox to itself:** whoever talks in a
  project's tasks runs commands in its sandbox and reads all it holds;
  the credential gate judges a sandbox by its own users, so it can't see
  people who reach it through another project.
- **A rested task without a pull request is "needs you"** (its answer
  waits for a person or the coordinator); a cancelled one is "done".
- **Not chosen:** a column for a project's pending sandbox request (a
  setting `proj_sbx_new:<pid>` holds it until the sandbox job made it); a
  per-run status column for the gate (the pending state carries it).

## Owner questions

- **Whose authority binds a task to the project's sandbox?** Built: the
  project owner's (above), with the owner a participant of every task.
  The consequence: every participant of a project runs commands in the
  owner's sandbox (as they already did by messaging the owner's own
  tasks, whose sharing is the project's), and so reads everything in it
  — **including the scm credentials K's gate wrote there for any other
  project in that sandbox** (`H/.config/xbin-scm/<uid>/`). K's §9.2 bot
  gate judges "every user of the sandbox" by the sandbox's own ACL, so it
  can't see people who reach the sandbox through another project's
  tasks: alice's private project B beside her shared project A would get
  B's bot token, readable by A's participant carol. Built against that:
  a shared project has its sandbox to itself, and no project joins a
  sandbox a shared one holds (409 `sandbox-shared`, see Deviations).
  Choosing the creator's authority instead (the spec's text) would not
  close this, since a participant reaches the owner's tasks anyway; it
  would only refuse a participant's own tasks on a sandbox they aren't a
  member of (403 at create). K and the lead should decide whether the
  rule belongs in K's gate as well (a project's people as the sandbox's
  users), and whether a looser rule is wanted: projects with exactly
  the same people could share a sandbox safely, which this rule refuses.
- **What does removal from a project take away?** Built: the project's
  routes and `/runs/{id}/task/…`; the conversations of tasks the person
  created stay theirs (V1), so they can still read them and write to
  them — which runs the task in the project's workspace. The alternative
  is re-owning those conversations to the project's owner on removal.
