## Changelog text

**Projects** (agent template, API.md §Projects): a project is a coding
sandbox, its repos (bare bases in the sandbox, cloned from the bound scm
provider), a policy and task conversations. `POST /projects` checks the
provider, the repos (the scm bot rule where the home works as the bot)
and the sandbox, then prepares the workspace in the background; `POST
/projects/{pid}/tasks` makes a task — its own conversation with a git
worktree per repo on its own branch, a range of ports, the repos' setup
run for it — answered by the built-in agent or a coding agent. A task's
turn waits at the workspace gate until its checkout is ready, at most
`maxTasks` tasks work at once (the rest wait in the project's queue), and
what a task pushes or opens as a pull request is noticed after each turn.
Tasks never run with internal reach; a project's conversations share its
sharing and stay in its space. Cleanup refuses unpushed work unless the
conversation's owner forces it. Additive: an older build leaves the new
tables alone and lists no task conversations among its chats.

## Decision text

- **One worker per engine owner, jobs in the database:** epoch-fenced
  claims and execs found again by `clientId` survive a handover; the
  scripts take every value through env.
- **The gate parks, it never consumes:** a parked task keeps its inbox;
  the park ends in the gate itself once the workspace is ready (the run
  rests and the pass goes on), so no wake row is queued — none can be left
  over — and a workspace change pokes the run so the park follows it. A
  turn in flight is never parked.
- **Slots count runs, not workspaces:** a task holds a slot while its run
  is active, parked at the gate or waiting for a person (V5); a person's
  own message bypasses the queue.
- **A rested task without a pull request is "needs you"** (its answer
  waits for a person or the coordinator); a cancelled one is "done".
- **Not chosen:** a column for a project's pending sandbox request (a
  setting `proj_sbx_new:<pid>` holds it until the sandbox job made it); a
  per-run status column for the gate (the pending state carries it).

- §16.2 edits: the 409 on a project run's own sharing is in

- §6.11: a task whose turn ended without a pull request is column
  `needs-you`, state `needs-you`, `waitingFor: "you"`; a cancelled task is
  column `done`, state `cancelled` (the spec named neither).
- §8.3 `bind`, §8.6: the gate ends its own park (the run goes idle, the
  pass goes on) and `bind` queues no `inboxWake` — it pokes the run (a
  takeover pokes a parked run too). A wake row could be left over when the
  pass that ended the park had read the inbox before `bind` committed, and
  start a turn nobody asked for later; a coding agent's would restart its
  adapter without a prompt. A turn in flight, or a resting run with no
  input, is never parked. A workspace state change pokes the task's run.
- §8.3 `bind`: a coding agent's first prompt gets the brief when the
  workspace is ready (its start row, client id `proj-start:<pid>:<n>`, is
  rewritten then), since the start is queued before the paths are known.
- §8.3 `sandbox` `{new}`: the request waits in the setting
  `proj_sbx_new:<pid>` until the job made the sandbox (no column for it).
- §8.1 `policy.engine` `auto`: "the person's last coding agent" is the
  coding agent of their latest coding-agent conversation (the backend
  keeps no `prefs/agent`).
- §8.5: `projectEnv(run, home)` — the call sites pass the sandbox's home
  (`GH_CONFIG_DIR` is under it).
- §8.3 `refs`: one an scm event asks for (`projectRefsCheck`) reads the
  branch's pull requests even when `prs` holds an open one, and runs once
  more if asked while running. Cleanup's `force` and this mark ride in the
  job's `client_id` (`force`, `read-pulls`).
- §8.4: a job not done 3 h after it was queued fails; a task waits at most
  20 min for its person's sign-in, then fails with Retry (so a partition
  isn't held up by a wait nobody answers).
- §10.5 `userWake`: an undelivered `wake=1` event counts only for a
  coordinator that exists (P1 writes such events before C makes one).
- §9.6 `projectsInSandbox`: every project of the sandbox, archived and
  deleting ones too (scrubbing more is safe).
- §8.7: the status page's slots warning compares `maxTasks` with the
  model calls built-in tasks may make (the gate's limit less a person's
  last slot), whatever `policy.engine` but `harness`.
- §6.14: a deleted project's tasks are cleaned up only when its sandbox
  stays; a cleanup refused for unpushed work leaves that worktree. Its
  subscriptions end through `runDeletedHooks` (every task conversation is
  deleted), the seams having no project-deleted hook.
