## Changelog text

- builtin-templates: **scm-github**, a new template (`bx template new
  scm-github`) that provides the new **`scm`** service ([scm.md](/docs/scm.md),
  protocol 1) from a GitHub App: repo credentials for sandboxes — each
  person's own GitHub sign-in (the device flow), kept in their partition,
  or the App's bot — repos, pull requests, issues, CI (workflow runs, jobs,
  steps, logs of completed jobs, annotations, reruns as a person) and
  conditional polling. Managers create the App from a manifest or paste
  one, and set a policy (which accounts and repos it serves, whether
  people may use the bot, workflows, reruns, a token-life cap). Webhook
  events follow (G2).
- docs: **scm.md**, the scm contract; partitions.md says a provider may be
  partitioned itself.

## Decision text

- **A partitioned provider:** the App (keys, installation tokens, setup,
  policy, the identity directory) at global; each person's sign-in in
  their partition, its refresh token never leaving it; an unpartitioned
  copy is bot-only. Not chosen: people's tokens at global (one place to
  steal every sign-in from), or an OAuth web flow (needs the client secret
  in every partition and a public callback per person).
- **Global holds the client secret, so global scopes and revokes;** a
  partition refreshes itself (a device-flow token needs no secret). The
  relay's body is the person's own input — their frame can send it — so
  global recomputes permissions, accounts and repos itself.
- **The identity directory comes from GitHub's answer** for a token only
  this App issued (`POST /applications/{client_id}/token`), never
  `GET /user`, which any token answers.
- **The epoch:** person tokens expire at the parent's expiry less an hour;
  the parent refreshes only when that can't cover a request (its margin:
  15 minutes, or its `minTtlSec`) — every token of a person rotates
  together. Not quite independent of whether a scoped token outlives its
  parent's refresh (undocumented): a request asking more than 10 minutes'
  margin refreshes the parent before the epoch's other tokens reach their
  `refreshAfter` — up to 40 minutes early at the 50-minute ceiling, 5 at
  the default — and were scoped tokens to die with their parent, those
  would die that much early. Owed with S2's live check; if S2 is
  negative, refresh only at the epoch's `refreshAfter` and serve the
  earlier window from the parent's remaining life.
- **A partition's token cache follows global:** conf `public` carries the
  policy's public half (now with `botRepos`) and a `tokenGen` that a
  policy change, Revoke all and a new App move; a partition re-checks
  every request against the half and reuses only tokens of the current
  generation. Not chosen: no caching in the partition (a relay and a mint
  per git operation).
- **Bot tokens per consumer and purpose,** narrowed to the asked repos and
  a preset; the tile's own reads and writes use internal tokens never
  handed out; `botRepos` holds reads too.
- **Reruns are a person's, never the bot's,** with the person's own
  sign-in in their partition.
- **Logs only for completed jobs** (`in-progress` with the live page):
  GitHub has no public partial-log API.
- **Spikes** answered from GitHub's documentation and owed a live check
  (below).

- §5.10 note (fix round 2): GitHub's rate limit is tracked per identity
  and resource (`X-RateLimit-Resource`): a spent search limit no longer
  blocks the identity's REST calls.
- §5.8 (fix round 3, supersedes the 404/422 above): only GitHub's 404 to
  a revocation is "already gone". GitHub documents 422 as "validation
  failed, or the endpoint has been spammed", so on a 422 global asks
  GitHub about the token (`POST /applications/{clientId}/token`, as
  `/partition/identity` does) and answers 204 only when that check
  answers 404 (corrected in fix round 4: round 3 also took the check's
  own 422 as "unknown"); otherwise 503 `unavailable` (`retryAfterMs`
  60000) and Forget clears nothing. `/partition/revoke-token` shares the
  path (best effort: its answer is ignored).
- §5.8 (fix round 4): Forget refreshes the pair first once the access
  token is within a minute of its expiry — GitHub no longer knows an
  expired token, so revoking with it would answer 404 and leave the grant
  (and its ~6-month refresh token) authorised. The grant is then revoked
  with the new token. A refresh GitHub refuses (`bad_refresh_token`) or a
  refresh token past its own expiry leaves nothing to revoke with: Forget
  clears and answers 204. Any other refresh failure is answered, nothing
  cleared. No refresh token (GitHub's "expire user tokens" off): the
  access token is used as is. The spec says only "revokes the grant
  upstream". (Live, 2026-10-04: GitHub refuses a revoked grant's refresh token with
  `incorrect_client_credentials`, which now ends the sign-in too when
  GitHub no longer knows the access token — records/LIVE.md.)
- §5.10 note (fix round 3): the rate resource is read from the API's root
  (past a GHES `/api/v3`): `search` only for `/search/…`, `graphql` only
  for `/graphql` and GHES's `/api/graphql`. GraphQL on a GHES is called at
  `https://<host>/api/graphql` (it was `…/api/v3/graphql`, which a GHES
  doesn't serve; github.com is unchanged).
